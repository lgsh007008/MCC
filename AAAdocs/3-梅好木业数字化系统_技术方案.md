
## 0. 文档使用说明

### 0.2 文档体系与优先级

| 文档                              | 回答                           | 组织维度      | 可变性   |
| ------------------------------- | ---------------------------- | --------- | ----- |
| 产品文档                            | What/Why：需求、约束、验收标准、**页面设计** | 按需求       | 高     |
| ADR（`AAAdocs/2-adr.md`）          | 为什么定死：不可逆决策                  | 按决策编号     | 只增不改  |
| 本技术方案                           | 全局怎么做：约定、边界、规范               | 按关注点（跨模块） | 随实现更新 |
| 模块设计（`AAAdocs/design/<module>.md`） | 该模块具体怎么做：表结构、接口清单、状态机、算法     | 按模块       | 随需求迭代 |

**优先级（冲突时以此裁决）**

```
产品文档（What/Why，需求与约束）
      ↑ 引用（R-xxx-NNN）
ADR  >  本技术方案（全局约定）  >  模块设计文档（模块实现）
```

**说明**：ADR 最高；本技术方案是其执行展开，并约束所有模块设计文档

### 0.3 三条铁律

1. **正文只放当前真相**（"现在是什么样"），历史脉络走文末 changelog；
2. **单一事实源**：每条信息只在一处定义，他处只引用不复制（复制必漂移）；
3. **文档只放约定与指针**：完整表结构归 `packages/db` 的 schema、API 细节归代码生成的 OpenAPI、AI 行为规则归 §13——本方案只放**概览 + 约定 + "详见 XX"**。

### 0.4 变更机制

新增或修改技术决策 → 先更新本方案对应章节 → 在 §15 Changelog **追加一行**（列：位置 / 类型 / 原本 / 现在 / 原因；类型仅取「新增」或「修改」）。

**版本小节命名格式**：`v<YYYYMMDD>（说明 · YYYY-MM-DD）`，如 `v20261015（初稿 · 2026-10-15）`。同日发生第二次变更时，版本号加后缀 `-2`（如 `v20261015-2`）。

**纪律**：版本一经冻结，其历史行**不得修改**；后续变更一律在文末**追加新版本小节**。

### 0.5 模块设计文档（第三层）

- **定位**：单个模块（业务领域）的技术实现设计——主体为**后端**（数据模型细节、接口清单、状态机、算法与关键流程），另含**"前端实现"节**；位于 `AAAdocs/design/<module>.md`，**每模块一份**。
- **与需求的关系**：需求是"改它的动作"，不是"它的单位"——一个需求通常只更新一份（跨模块时更新多份），**不新增文件**；模块数量增加时才新增文档。
- **创建时机**：该模块**第一个真实需求**到来时创建，**不预生成空模板**。
- **纪律**：正文只放当前真相，自带 changelog（**格式同 §15**：位置 / 类型 / 原本 / 现在 / 原因；已冻结版本历史行不得修改）；引用需求编号（`R-xxx-NNN`）与相关 ADR；**只写本模块特有内容**，全局约定一律回本方案，不重复。

#### 页面设计的归属（属"设计"层，不在本文件）

- 页面设计（这一页要有什么、怎么排、怎么交互）**归产品文档**，作为对应需求的一部分——需求改则页面随之改，天然同步。
- 与"前端实现"的区别：页面设计=设计意图（人写，属 What）；前端实现=技术落地（AI 写，属 How）。

#### "前端实现"节的内容（本文件内）

该业务领域在**前端侧的技术落地设计**——回答"前端代码怎么组织"，而不是"页面长什么样"；它是"页面设计（产品文档）"与"前端规范（§9）"之间的翻译层。**只在存在非平凡前端逻辑时写**（纯 CRUD 页面用现成组件拼即可，不为它单开一节）。

**应写（6 项）**

1. **页面 / 组件清单**——本领域涉及哪些页面与组件（报价页、报价结果页、报价列表…）；
2. **数据来源**——每个页面调哪些接口（引用本模块的接口清单）、取数时机（服务端渲染 / 客户端请求）；
3. **客户端状态**——本领域特有的前端状态（报价草稿、多步表单中间态、未提交的编辑）；
4. **交互逻辑**——非平凡交互（实时联动刷新总价、防重复提交、错误提示与回退）；
5. **组件复用**——用哪些已有组件、是否需新增（新增受 §9 纪律约束）；
6. **可见性与权限**——哪些元素按角色 / 身份隐藏或禁用。

**不写（防越界）**

- 颜色 / 字号 / 间距 → 令牌（§9）；
- "这页有哪些字段、怎么排" → 页面设计（产品文档）；
- 接口定义 → 本模块接口清单（同一文档的后端部分）。

#### 跨模块页面（归属与接口引用）

- **页面归属唯一**：一个页面必须且只能归属一个领域——判定看它**围绕哪个实体 / 业务动作**展开（如"订单详情页"虽展示报价与生产信息，主实体是订单，归 `order`）；拿不准时用**变更检验**（该页面会随哪个领域的需求变化而改）。**一个页面只能在一份模块设计文档里被描述**，禁止两份各写一半（否则即成"两份真相"）。
- **接口引用可跨模块**：数据来源项列出该页面调用的**所有**接口并标注归属模块，**只引用、不重述定义**（定义留在各模块的接口清单）。
- **数据聚合**：优先**客户端并发调用 + 客户端组合**（MVP 首选）；聚合逻辑复杂或需权限裁剪时，由**页面所属领域**提供**只读聚合接口**，内部只调其他模块的公开接口。
- **禁止**：新建"聚合模块"直接读他模块的表——属边界穿透，违反 ADR-001。

## 当前状态速览

> 给 AI 的快速入口（半页）。每次开发只必读本节 + 本次相关章节。

- **形态**：单仓库 monorepo（pnpm workspace + Turborepo）+ 单一后端模块化单体（NestJS）+ 独立 Agent 服务。
- **语言**：全栈 TypeScript。
- **数据**：PostgreSQL（业务 + pgvector 向量）· Redis（缓存/队列）· S3 兼容对象存储。
- **前端**：Next.js（网站 + 管理后台）· Taro（小程序）· Tailwind + shadcn/ui + 设计令牌。
- **三条全局禁令**：① 任何模块禁止直接读他模块的表；② 任何客户端与 Agent 禁止直连数据库；③ 密钥禁止出现在前端可见变量中。
- **最高依据**：`AAAdocs/2-adr.md` 中 9 条 ADR。

## 1. 系统概述

> 只描述**技术组件构成与职责边界**，不涉及任何业务功能。

### 1.1 技术组件全景

```
┌── 客户端层 ───────────────────────────────────────────┐
│  web（Next.js）        miniapp（Taro）      第三方/开放调用方 │
└──────────────────────────┬───────────────────────────┘
                           │ HTTP（统一业务 API）
┌── 服务层 ────────────────▼───────────────────────────┐
│  server：模块化单体（NestJS）                          │
│  ├ 业务模块 · 各自 Controller/Service/表              │
│  ├ 横切中间件：鉴权 · 审计 · 限流 · 错误处理           │
│  └ OpenAPI 契约（代码生成）                            │
└──────────┬───────────────────────────┬───────────────┘
           │ 内部接口/事件              │
           │                    ┌──────▼───────────────┐
           │                    │ agent 服务            │
           │                    │ MCP Server → 调业务API │
           │                    └──────────────────────┘
┌── 数据层 ─▼───────────────────────────────────────────┐
│  PostgreSQL（业务 + 向量）  Redis（缓存/队列）  S3对象存储 │
└───────────────────────────────────────────────────────┘
```

### 1.2 组件职责边界（硬规则）

| 组件 | 职责 | 硬边界 |
|---|---|---|
| web / miniapp | 展示与交互 | 只经统一 API 取数据；**不直连数据库** |
| server | 全部业务逻辑、数据读写、审计 | **唯一**访问数据库的进程 |
| agent | 对话理解、工具编排 | 只经 MCP → 业务 API；**不直连数据库**、不内嵌业务规则 |
| 数据库 | 数据持久化 | 只被 server 访问 |

### 1.3 通信原则

- **人类流量**走统一业务 API（HTTP）；**Agent 流量**走 MCP → 同一套业务 API；两股客流在服务层汇合。
- 模块之间**只走公开接口/领域事件**，禁止跨模块穿透（详见 §5）。

## 5. 模块划分与边界规则

### 5.1 模块四件套模板

```
modules/<domain>/
├── <domain>.controller.ts   # 对外 HTTP 入口（API）
├── <domain>.service.ts      # 业务逻辑
├── dto/                     # 入参/出参类型（zod/class-validator）
├── <domain>.module.ts       # NestJS 模块声明
└── index.ts                 # ★ 唯一公开出口：显式导出供他模块使用
```

### 5.2 三条硬规则

1. **自有资产**：每个模块拥有自己的 Controller、Service、数据表；
2. **公开接口**：跨模块只能调用对方 `index.ts` 导出的内容，禁止直接读对方的表；
3. **禁止穿透**：禁止 import 对方内部实现（如 `../<domain>/<domain>.service`），只许 `../<domain>`（即 index）。

**强制手段**：eslint 边界规则（`eslint-plugin-boundaries` 或等价方案）在 CI 中拦截上述违规。

### 5.3 划分方法（判断新模块归属的四检验）

1. **名词法**：核心业务名词每个有且只有一个"家"；无家者应开新模块，两家相争说明划错；
2. **变更检验**：一个业务变化只应改动一个模块；
3. **业务对话检验**：业务人员的天然分工即领域边界；
4. **拿不准就合并**：数据所有权清晰前提下，模块内部后拆易，模块之间先拆难。

**反向警告**：不按技术分层划模块（不得出现 controller 模块 / service 模块）；不划太碎（正常 5~8 个，随领域数量）。

### 5.4 模块清单与设计的维护位置

- **业务结构**（模块清单、领域地图）：维护在**产品文档**；
- **模块技术设计**（表结构、接口清单、状态机、算法）：维护在 **`AAAdocs/design/<module>.md`**（每模块一份，随需求迭代生长；创建与纪律见 §0.5）。

本方案只规定划分规则与边界纪律。技术侧约束：**数据所有权从首次建表起就必须清晰**。

### 5.5 模块间通信

- **同步**：调用对方的公开 Service 接口；
- **异步**：发领域事件（记录到事件日志表），他模块按需消费；
- 禁止：跨模块直连数据库、跨模块共享可变状态。

## 6. 数据模型概览

> 只放通用设计约定；**完整表结构见 `packages/db/schema.prisma`**，业务字段语义见产品文档。

### 6.1 概念关系（示意）

```
[业务实体A] ──1:N──► [业务实体B] ──1:N──► [业务实体C]
      ▲                                        │
      └────────── 领域事件日志（全局） ◄────────┘
```

（具体实体与基数以 schema 与产品文档为准。）

### 6.2 通用字段约定（全表适用）

| 约定 | 说明 |
|---|---|
| `tenant_id` | **全表预留**（ADR-005），现单租户恒为默认值，为 SaaS 化留位 |
| 主键 | 统一采用不可推测的全局唯一 ID（具体算法脚手架锁定） |
| `created_at / updated_at` | 全表必备，UTC 存储 |
| 软删除 | 业务数据用 `deleted_at`，禁止物理删除（审计与恢复需要） |
| 金额/尺寸 | 用精确数值类型（Decimal），**禁止浮点** |
| 单位 | 长度、重量统一基准单位存储，展示层换算 |

### 6.3 模式约定

- **状态机模式**：有生命周期的主实体（如订单）用显式状态字段 + 状态流转表，禁止在业务代码里散落 `if status ==`；
- **事件日志表**：全局记录领域事件（谁、何时、对什么、做了什么），供审计与未来新模块消费；
- **审计字段**：写操作记录操作者身份（含 Agent 的 service account）。

### 6.4 纯函数区域（对应 ADR-004）

计算类逻辑（计价等）为**纯函数**，无副作用、不直接写库：输入 → 输出，结果由调用方决定是否持久化。好处：可单测、Agent 易调用、未来可独立拆出。

### 6.5 迁移纪律

- 只向前迁移；删列/改列走"先加新列 → 双写/回填 → 切读 → 再删旧列"；
- 迁移脚本先过 staging 再过 prod；
- **禁止修改已应用的历史迁移文件**。

## 7. API 契约规范

### 7.1 风格与生成

- REST 风格，全量契约由 NestJS 装饰器**代码生成** OpenAPI（ADR-006）→ 产出 `openapi.json` → 生成 `packages/shared` 中的类型化 client；
- **契约与实现永远同步**，禁止手写与实现脱节的接口文档。

### 7.2 命名与版本

| 项 | 约定 |
|---|---|
| 路径 | 资源小写复数、kebab-case：`/api/v1/quote-orders` |
| 版本 | URL 中带主版本 `/api/v1`，仅破坏性变更升版 |
| 动作 | 尽量用 HTTP 语义（GET/POST/PUT/PATCH/DELETE），非 CRUD 动作用子资源表达 |

### 7.3 请求约定

- 分页：统一 `page`/`pageSize`（或 cursor，二选一并全站一致）；
- 排序/过滤：统一查询参数命名，禁止各接口自定义；
- 幂等：会重复提交的写操作（如创建）支持 `Idempotency-Key` 请求头。

### 7.4 响应与错误

- 统一响应结构（成功 / 失败一致的外层）；
- 错误采用统一体（建议 RFC 7807 `application/problem+json`）：`code`（机器可读）+ `message`（中文人可读）+ `details`；
- 禁止把内部异常栈或数据库信息返回给调用方。

### 7.5 语义化纪律（Agent 可理解的关键）

- **枚举禁止魔法数字**：状态值用可读字符串或带 `description` 的枚举，不用 `3` 代表"待发货"；
- 每个字段的 `description` 写**业务语言**（如"出材率：成品体积/原木体积"），不写技术语言；
- 维护一份 **业务术语表**（业务词 ↔ 系统字段/枚举），供 Agent 与文档引用。

### 7.6 变更与废弃

- **只做增量变更**：加字段/加接口自由；破坏性变更走升版 + 双写过渡 + 显式废弃期；
- 废弃接口须标注并保留过渡期，禁止突然删除；
- 契约变更须人工过目（多端与 Agent 共用同一契约，改动面广）。

## 8. Agent 集成

### 8.1 集成路径（唯一路径）

```
业务 API ──自动生成──► MCP Server（工具注册） ──► Agent ──调用──► 业务 API（与 UI 同源）
```

**原则**：不为 Agent 单开通道。每上线一个业务功能，Agent 自动获得对应能力。

### 8.2 五条军规

1. Agent 永远走 API，**不直连数据库**；
2. 工具由 OpenAPI 契约**自动生成**，禁止手工维护一套与实现脱节的工具定义；
3. MCP Server 作为适配层，换 Agent 框架不动业务代码；
4. 计算类能力（如计价）以纯函数模块暴露为工具，输入输出明确；
5. Agent 用**独立 service account** + **全量审计日志**（可回溯、可追责、可限流）。

### 8.3 权限三阶段（放权刻度）

| 阶段 | 权限 | 晋级依据 |
|---|---|---|
| 一 · 只读观察 | 仅查询 | 连续观察期查询准确率达标 |
| 二 · 受限写 + 审批 | 可写，敏感操作（大额/新实体）强制人工审批 | 审批通过率与异常率达标 |
| 三 · 自主 + 抽检 | 常规操作自主，异常上浮，日志支撑抽检 | 抽检合格率稳定 |

晋级标准写入业务规则（产品文档），本方案只规定**技术支撑**：每阶段用**权限 scope** 实现，可由配置切换。

### 8.4 语义层

Agent 依赖 §7.5 的语义化契约 + 业务术语表；知识库（显性知识进 RAG，历史业务数据作案例库）建设属业务侧规划，技术侧已预留 pgvector。

## 9. 前端规范

### 9.1 设计令牌（Design Tokens）

- 令牌定义于 `packages/tokens`，web 与 miniapp 共用**同一份源**；
- 令牌覆盖：颜色、字号、间距、圆角、触控目标尺寸、对比度；
- **禁止**在业务代码写死具体值（`#0FDC78`、`16px`），一律引用令牌（对应 ADR-008）。

### 9.2 组件库纪律

- 组件一律来自组件库（shadcn/ui，源码入库） + 令牌；
- 第三方组件库（如 antd）仅当局部复杂表格查询确需时**按需引入**，引入须记 changelog；
- 禁止裸写内联样式、禁止 `!important` 覆盖。

### 9.3 断点（响应式）

- 全站统一断点档位（如 `sm/md/lg/xl`），禁止页面各写各的判断；
- **移动优先**书写（默认移动端，向上覆盖）。

### 9.4 适老切换机制

- 定义**两套令牌取值**：标准模式 / 关怀模式（放大字号、增大触控目标、提高对比度）；
- 切换 = 套用另一套令牌，一处切换全局生效；
- 用户偏好**存后端账号**，换设备生效；
- 说明：小程序内字体受平台限制，切换的是版式与令牌，不接管系统字体。

### 9.5 数据与状态

- 服务端状态统一走查询库（如 TanStack Query）管理缓存与失效，不用全局 store 硬存服务端数据；
- 表单校验复用 `packages/shared` 的 zod 定义（前后端同一份）。

## 10. 认证与安全

### 10.1 身份与凭证

| 主体 | 凭证方式 |
|---|---|
| 人（web/miniapp） | 登录后签发访问令牌（短期）+ 刷新令牌（长期），全端统一 |
| Agent | 独立 **service account** 凭证（客户端凭证模式） |

- 密码存储：强哈希（argon2 或等价方案），禁止可逆存储；
- 传输：全站 HTTPS。

### 10.2 权限模型

- **RBAC**：角色 → 权限（scope）；Agent 亦按 scope 授权（对应 §8.3 三阶段）；
- 权限校验统一在服务层守卫中完成，不在前端做安全判断。

### 10.3 密钥与环境变量规则

- git 中只保留 `.env.example`；真实 `.env` 一律 ignore；
- `.env` **按 app 分散持有**（`apps/web/.env.local`、`apps/server/.env`、`apps/agent/.env`）；
- **local** 用真实 `.env` 文件；**staging/prod** 用部署平台环境变量注入，**服务器上不落文件**；
- **红线**：前端框架中"公开前缀"变量（Next.js 的 `NEXT_PUBLIC_`）会打进浏览器包，**密钥绝不许加此前缀**；
- `.env` 相关 diff **一律人工过目**。

### 10.4 边界防护

- 所有外部输入在服务层边界用 zod 校验；
- 统一限流（按主体/接口），写入类与登录类重点防护；
- 敏感文件走**签名 URL + 私有读写**，禁止可猜测的公开路径。

### 10.5 审计

- 全量写操作 + 全部 Agent 调用记录审计日志（主体、时间、对象、动作、结果）；
- 审计日志不可篡改、只增。

## 11. 环境与部署

### 11.1 环境分层

| 环境 | 位置 | 数据库 | 用途 |
|---|---|---|---|
| local | 本机 | Docker 起的 PG/Redis | 本地开发自测 |
| staging | 云服务器 | 独立测试库 | 真机验收（含小程序体验版） |
| prod | 云服务器 + 托管 RDS | 正式库 | 真实数据 |

### 11.2 核心规则

- **区分环境的是配置不是代码**：代码只有一份（main），差异全在配置；
- 测试库与生产库**物理隔离**，绝不共用连接串；
- 配置载体见 §10.3（local 文件 / staging、prod 平台注入）。

### 11.3 部署

- 开发环境：`docker compose up` 起 PG + Redis；
- 生产：应用容器化部署，**数据库用托管 RDS**（自动备份、可回滚）；
- 发布流向：功能分支 → main → 自动部署 staging → 验收 → 打 tag → 部署 prod（单向）。

### 11.4 迁移与发布纪律

- 迁移只向前，先 staging 后 prod（详见 §6.5）；
- 生产数据进测试环境必须**脱敏**。

## 13. 编码规范（AI 行为约定）

> 本节是 AI 行为约定的**唯一载体**，记架构层禁区；冲突以 ADR 为准。

### 13.1 通用约定

- TypeScript `strict` 全开；禁止滥用 `any`（必要时显式标注并说明理由）；
- 目录与命名遵循 §4、§5 模板，禁止自创结构；
- 复用优先：类型、校验、client、令牌一律取自 `packages/*`。

### 13.2 禁止清单（Review 重点）

1. 跨模块穿透 import（绕过 `index.ts`）；
2. 客户端/Agent 直连数据库；
3. 在业务代码写死样式值或使用内联样式覆盖；
4. 密钥出现在前端公开变量（`NEXT_PUBLIC_*`）；
5. 枚举用魔法数字；
6. 破坏性 API 变更（未升版/未过渡）；
7. 修改已应用的历史迁移文件；
8. 为赶进度绕过统一 API、自建旁路数据通道。

### 13.3 生成纪律

- **方案预审**：实现前先列方案与取舍，确认后再写码；
- **diff review**：每次生成对照本节禁止清单逐条检查；
- 涉及 `.env`、契约、迁移的 diff 一律人工过目。

## 14. 技术简化决策

> 只登记**技术取舍**（"暂未引入 X，因为 Y，触发条件是 Z"）。业务功能取舍不在此处（见产品文档）。

| 项 | 现状 | 触发引入条件 |
|---|---|---|
| 独立 API 网关 | 暂不引入，单体中间件承担鉴权/限流/审计 | 多租户开放 API、需独立计量/开发者门户时 |
| 独立缓存层 | 暂不引入 | 量级达到需缓存复用时 |
| 自动化 CI | 先手动部署 | 迭代频率提升后补齐流水线 |
| 热点计算独立 Worker | 暂与主进程同跑 | 计算类任务影响主链路响应时 |
| 独立搜索服务 | 暂用数据库承担 | 检索复杂度超出数据库能力时 |
| Agent 独立语言 | 暂用 TS | 生态瓶颈无法绕开时（届时仅 agent 服务独立） |
