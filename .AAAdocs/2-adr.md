# 架构决策记录（ADR）

***

## 使用规则

1. **编号即身份**：`ADR-NNN` 一经分配永不改变、永不复用。
2. **只增不改**：已采纳条目的决策内容不得修改。
3. **变更与撤销**：原条目**正文不改**，变更只落在头部一行——被取代则追写 `状态：已被 ADR-NNN 取代`，作废则追写 `状态：已废弃`。
4. **条目结构**：状态 / 上下文（当时的约束与理由）/ 决策 / 后果。

## ADR-001：模块化单体，不上微服务

- 状态：已采纳（2026-10-15）

**上下文**

- 开发形态为单人 + AI，不存在多团队并行的组织诉求——而微服务解决的是组织协作问题，不是技术问题。

- 引入微服务会带来分布式事务、服务编排、链路可观测等复杂度；在没有团队规模收益时，这些属纯负担。

- 但业务领域边界需长期可拆（未来热点模块独立扩展、SaaS 化输出），要求模块边界从第一天起就具备可分离性。

**决策**

后端为**单一部署单元**的模块化单体；内部按业务领域划分模块，模块间只经公开接口与领域事件通信，**禁止跨模块直连数据表或引用对方内部实现**；边界纪律由 lint 规则在 CI 中强制。

**后果**

- 一次部署、单数据库，迭代速度最快。

- 主要风险从技术复杂度转为边界纪律——一旦被穿透，未来可拆即失效，故以 lint 强制。

- 未来可按需将热点模块拆为独立服务，接口不变，主体不受影响。

## ADR-002：API-first——UI 与 Agent 平级消费同一套 API

- 状态：已采纳（2026-10-15）

**上下文**

- 系统需同时服务于人类（网站 / 小程序）与 Agent。

- 若为 Agent 单开一套通道，将产生两套业务逻辑与双份维护，且长期必然不一致。

- Agent 的长期目标是直接使用企业系统（增强或替代人的操作），这要求系统对它**可调用、可理解**。

**决策**

全部业务能力收敛为**统一业务 API**；网站、小程序、Agent 均为该 API 的**平级消费者**；Agent 经 MCP 适配层调用同一 API，**不直连数据库、不旁路**。

**后果**

- 新增业务功能自动同时对人、对 Agent 可用，无需为 Agent 单独开发。

- API 无状态，便于横向扩容。

- 代价：契约稳定性成为强约束——契约乱改会同时影响网站、小程序与 Agent 三端。

## ADR-003：全栈 TypeScript

- 状态：已采纳（2026-10-15）

**上下文**

- 单人 + AI 维护全系统；跨语言会切断类型链路、增加 AI 的上下文切换成本、降低生成质量。

- 需最大化利用 AI 的语料优势，并借助编译器在生成阶段自动暴露类型错误。

**决策**

前端（Next.js / Taro）、后端（NestJS）、数据访问客户端（Prisma）与 Agent 服务**统一使用 TypeScript**（`strict` 全开）。

**后果**

- 建立类型共享链路（schema → shared → 各端），字段变更时三端同时编译报错，防止静默漂移。

- AI 生成质量与自检能力提升。

- 代价：重计算场景可能需外挂非 TS 实现。

## ADR-005：tenant\_id 全表预留

- 状态：已废弃（2026-10-15）——无多租户 / SaaS 规划，全表预留属投机性预留

**上下文**

- 业务可能在未来向同行业输出（SaaS 化），届时需要多租户隔离。

- 事后再为全表补 `tenant_id` 并回填历史数据，代价极高、易遗漏、易出错。

**决策**

所有业务表**自建表起即包含** **`tenant_id`**；当前单租户场景恒为默认值。

**后果**

- 现在成本近零，为多租户开放预留前提。

- 代价：数据访问必须统一附加租户条件（在数据访问层集中处理，避免逐处遗漏）；并影响唯一索引与约束的设计。

## ADR-006：OpenAPI 契约由代码生成

- 状态：已采纳（2026-10-15）

**上下文**

- 前端（网站 / 小程序）与 Agent 都要调同一批接口；接口定义若靠人手写一份文档，迟早会跟真实实现不一致。

- Agent 调用接口时需要的工具说明，也必须和真实接口同源，不能另维护一套。

**决策**

接口定义**只写在后端代码里**，构建时自动生成 `openapi.json`；前端调接口用的类型化代码、Agent 用的工具说明，都由这份 `openapi.json` 自动生成；**禁止手写接口文档**（会与实现脱节）。

**后果**

- 接口定义有唯一事实源，网站 / 小程序 / Agent 三端永远跟实现一致，改字段时前端编译即报错。

- 代价：字段要写清楚（枚举用语义化名字、字段用业务语言描述）；因影响面广，接口改动需人工过目。

## ADR-007：差异化能力自建 / 通用职能外购，外购必走适配层

- 状态：已采纳（2026-10-15）

**上下文**

- 业务边界不确定，哪些能力自己做、哪些买现成的，现阶段还无法逐个拍板。

- 全部自建不现实；全部外购则会丧失竞争力与数据资产。

- 外购系统的数据模型若直接渗入自有数据库，会造成深度耦合，换供应商时代价巨大。

**决策**

- 判定规则：构成**竞争优势与数据资产**的能力自建；**通用职能默认外购**——确需自建时**新增一条 ADR 记录理由**（本阶段不预先枚举具体清单）。

- 外购系统一律经**适配层（反腐层）双向同步**接入，**外部数据模型不得进入自有库**。

**后果**

- 更换供应商只需替换适配层，主体系统不受影响。

- 自建范围被约束在护城河内，避免战线过长。

- 代价：需持续维护适配层，并处理同步一致性（含失败重试与对账）。

## ADR-008：UI 只许用组件库 + 设计令牌，禁止写死样式值

- 状态：已采纳（2026-10-15）

**上下文**

- 系统需响应式适配多端，并支持适老化（可切换的更大字号、更大触控目标、更高对比度）。

- 样式若写死具体值，则无法实现一处切换、全局生效。

- AI 生成代码时易图省事写入硬编码值或内联样式覆盖。

**决策**

视觉取值**全部抽取为设计令牌**（`packages/tokens`，多端共用同一份源）；UI 仅来自**组件库 + 令牌**；**禁止硬编码具体值与内联覆盖**。

**后果**

- 适老模式即切换另一套令牌，一处生效，全局同步。

- 多端视觉统一且可控，品牌一致性有保障。

- 代价：需维护令牌体系，并在 review 中拦截硬编码与内联样式。

***

## ADR-009：单仓库 monorepo

- 状态：已采纳（2026-10-15）

**上下文**

- 单人 + AI 开发；多仓库会切断类型共享链路、割裂 AI 的上下文视野，并使共享包的发版成本成为常态负担。

**决策**

采用**单仓库 monorepo**（pnpm workspace + Turborepo）。

**后果**

- 一次提交即可完成跨端一致改动，契约在仓库内不断裂。

- 代价：需维护 workspace 构建编排，仓库体积随项目增长。
