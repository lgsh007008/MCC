# 架构决策记录（ADR）

***

## 使用规则

1. **编号即身份**：`ADR-NNN` 一经分配永不改变、永不复用。
2. **只增不改**：已采纳条目的决策内容不得修改。
3. **变更与撤销**：原条目**正文不改**，变更只落在头部一行——被取代则追写 `状态：已被 ADR-NNN 取代`，作废则追写 `状态：已废弃`。
4. **条目结构**：状态 / 上下文（当时的约束与理由）/ 决策 / 后果。

## ADR-001：模块化单体，不上微服务

- 状态：已采纳（2026-10-15）

**上下文**

- 开发形态为单人 + AI，不存在多团队并行的组织诉求——而微服务解决的是组织协作问题，不是技术问题。

- 引入微服务会带来分布式事务、服务编排、链路可观测等复杂度；在没有团队规模收益时，这些属纯负担。

- 但业务领域边界需长期可拆（未来热点模块独立扩展、SaaS 化输出），要求模块边界从第一天起就具备可分离性。

**决策**

后端为**单一部署单元**的模块化单体；内部按业务领域划分模块，模块间只经公开接口与领域事件通信，**禁止跨模块直连数据表或引用对方内部实现**；边界纪律由 lint 规则在 CI 中强制。

**后果**

- 一次部署、单数据库，迭代速度最快。

- 主要风险从技术复杂度转为边界纪律——一旦被穿透，未来可拆即失效，故以 lint 强制。

- 未来可按需将热点模块拆为独立服务，接口不变，主体不受影响。

## ADR-002：API-first——UI 与 Agent 平级消费同一套 API

- 状态：已采纳（2026-10-15；移动端「小程序」表述已被 ADR-011 取代）

**上下文**

- 系统需同时服务于人类（网站 / 小程序）与 Agent。

- 若为 Agent 单开一套通道，将产生两套业务逻辑与双份维护，且长期必然不一致。

- Agent 的长期目标是直接使用企业系统（增强或替代人的操作），这要求系统对它**可调用、可理解**。

**决策**

全部业务能力收敛为**统一业务 API**；网站、小程序、Agent 均为该 API 的**平级消费者**；Agent 经 MCP 适配层调用同一 API，**不直连数据库、不旁路**。

**后果**

- 新增业务功能自动同时对人、对 Agent 可用，无需为 Agent 单独开发。

- API 无状态，便于横向扩容。

- 代价：契约稳定性成为强约束——契约乱改会同时影响网站、小程序与 Agent 三端。

## ADR-003：全栈 TypeScript

- 状态：已采纳（2026-10-15；前端 Taro 已被 ADR-011 取代）

**上下文**

- 单人 + AI 维护全系统；跨语言会切断类型链路、增加 AI 的上下文切换成本、降低生成质量。

- 需最大化利用 AI 的语料优势，并借助编译器在生成阶段自动暴露类型错误。

**决策**

前端（Next.js / Taro）、后端（NestJS）、数据访问客户端（Prisma）与 Agent 服务**统一使用 TypeScript**（`strict` 全开）。

**后果**

- 建立类型共享链路（schema → shared → 各端），字段变更时三端同时编译报错，防止静默漂移。

- AI 生成质量与自检能力提升。

- 代价：重计算场景可能需外挂非 TS 实现。

## ADR-005：tenant\_id 全表预留

- 状态：已采纳（2026-10-15 采纳并于同日废弃；2026-11-09 复活）——多租户 / SaaS 前提重新成立

**上下文**

- 业务可能在未来向同行业输出（SaaS 化），届时需要多租户隔离。

- 事后再为全表补 `tenant_id` 并回填历史数据，代价极高、易遗漏、易出错。

**决策**

所有业务表**自建表起即包含** **`tenant_id`**；当前单租户场景恒为默认值。

**后果**

- 现在成本近零，为多租户开放预留前提。

- 代价：数据访问必须统一附加租户条件（在数据访问层集中处理，避免逐处遗漏）；并影响唯一索引与约束的设计。

## ADR-006：OpenAPI 契约由代码生成

- 状态：已采纳（2026-10-15）

**上下文**

- 前端（网站 / 小程序）与 Agent 都要调同一批接口；接口定义若靠人手写一份文档，迟早会跟真实实现不一致。

- Agent 调用接口时需要的工具说明，也必须和真实接口同源，不能另维护一套。

**决策**

接口定义**只写在后端代码里**，构建时自动生成 `openapi.json`；前端调接口用的类型化代码、Agent 用的工具说明，都由这份 `openapi.json` 自动生成；**禁止手写接口文档**（会与实现脱节）。

**后果**

- 接口定义有唯一事实源，网站 / 小程序 / Agent 三端永远跟实现一致，改字段时前端编译即报错。

- 代价：字段要写清楚（枚举用语义化名字、字段用业务语言描述）；因影响面广，接口改动需人工过目。

## ADR-007：差异化能力自建 / 通用职能外购，外购必走适配层

- 状态：已采纳（2026-10-15）

**上下文**

- 业务边界不确定，哪些能力自己做、哪些买现成的，现阶段还无法逐个拍板。

- 全部自建不现实；全部外购则会丧失竞争力与数据资产。

- 外购系统的数据模型若直接渗入自有数据库，会造成深度耦合，换供应商时代价巨大。

**决策**

- 判定规则：构成**竞争优势与数据资产**的能力自建；**通用职能默认外购**——确需自建时**新增一条 ADR 记录理由**（本阶段不预先枚举具体清单）。

- 外购系统一律经**适配层（反腐层）双向同步**接入，**外部数据模型不得进入自有库**。

**后果**

- 更换供应商只需替换适配层，主体系统不受影响。

- 自建范围被约束在护城河内，避免战线过长。

- 代价：需持续维护适配层，并处理同步一致性（含失败重试与对账）。

## ADR-008：UI 只许用组件库 + 设计令牌，禁止写死样式值

- 状态：已采纳（2026-10-15；后果中「适老模式即切换另一套令牌」的落地口径已由 ADR-011 收窄为按端套用令牌，不做用户开关）

**上下文**

- 系统需响应式适配多端，并支持适老化（可切换的更大字号、更大触控目标、更高对比度）。

- 样式若写死具体值，则无法实现一处切换、全局生效。

- AI 生成代码时易图省事写入硬编码值或内联样式覆盖。

**决策**

视觉取值**全部抽取为设计令牌**（`packages/tokens`，多端共用同一份源）；UI 仅来自**组件库 + 令牌**；**禁止硬编码具体值与内联覆盖**。

**后果**

- 适老模式即切换另一套令牌，一处生效，全局同步。

- 多端视觉统一且可控，品牌一致性有保障。

- 代价：需维护令牌体系，并在 review 中拦截硬编码与内联样式。

## ADR-009：单仓库 monorepo

- 状态：已采纳（2026-10-15）

**上下文**

- 单人 + AI 开发；多仓库会切断类型共享链路、割裂 AI 的上下文视野，并使共享包的发版成本成为常态负担。

**决策**

采用**单仓库 monorepo**（pnpm workspace + Turborepo）。

**后果**

- 一次提交即可完成跨端一致改动，契约在仓库内不断裂。

- 代价：需维护 workspace 构建编排，仓库体积随项目增长。

## ADR-010：后端锁定 NestJS 12；自己只写「薄适配层」，核心算法用成熟库

- 状态：已采纳（2026-10-17）

**上下文**

- 项目起手时按「用最新稳定版」的习惯选了 NestJS 12。它是新版框架，只用新版模块格式（ESM），一批还没跟上的配套包因此用不了。这个影响后面所有开发的选择当时没有单独写下来，本条补上。

| 配套包                      | 用途            | 出的问题                   | 处理办法                               |
| ------------------------ | ------------- | ---------------------- | ---------------------------------- |
| @nestjs/throttler        | 全站限流          | 与 NestJS 12 不兼容        | 限流自己写（Redis 计数）                    |
| nestjs-zod               | 把 zod 校验接到接口上 | 与 NestJS 12 不兼容        | zod 继续用，接线的管道自己写                   |
| eslint-plugin-boundaries | 拦住跨模块乱引用      | 在 pnpm 布局下失效           | 自己写 eslint 规则（技术方案 §4.2 允许「或等价方案」） |
| tsx                      | 开发时加速运行       | 不支持装饰器元数据（与 Nest 版本无关） | 自己写启动器（loader）+ swc 编译             |
| argon2                   | 密码加密          | 安装时下载编译卡死              | 换 @node-rs/argon2（同为成熟库）           |
| @swc/core                | 编译代码          | 新版有权限 Bug              | 锁在 1.7.42 旧版（仍是成熟库）                |

**决策**

| 事项     | 决定                  | 解释                                                    |
| ------ | ------------------- | ----------------------------------------------------- |
| 框架版本   | 锁定 NestJS 12，不回退    | 回退到 11 只能修好上表前 2 个包，tsx 与 boundaries 的问题跟版本无关，白折腾一次降级 |
| 自己写的范围 | 只写「薄适配层」，核心算法尽量用成熟库 | 成熟库干真正的活，自己只写把它接到框架上的那层薄壳                             |
| 限流     | 维持自己写的 Redis 计数     | 换成熟限流库的方案评估过，已拍板维持现状                                  |

**后果**

- 自己写的部分只剩「薄壳」：逻辑浅、好审查；上游包修好后可随时换回官方包。

- 以后引入任何第三方包，先查三件事再安装：Node 版本是否支持、是否兼容新版模块格式、pnpm 布局下能否正常跑。

## ADR-011：移动端 = 移动 Web；适老化 = 移动端令牌基线，不做用户开关

- 状态：已采纳（2026-11-10）

**上下文**

- 现场操作（如在车间、装车点用手机录成品销售单）需要移动端界面；使用者是一线人员，存在老花、手抖、强光下看不清的现实约束。
- 原技术方案把移动端承载写成 Taro 小程序（`apps/miniapp`），但同类需求只是一个浏览器页面：小程序要额外的注册、审核与发布链路，而同一套 API 已可直接被手机浏览器调用。
- ADR-008 后果中「适老模式即切换另一套令牌」预留的是用户可见开关；实际诉求是「移动端默认就好用」，加开关反而多出入口与状态。

**决策**

- 移动端承载 = **同一 `apps/web` 内的移动路由组 `/m/**`（移动 Web）**：手机浏览器直接访问；不新开 app、不做小程序；与 PC 后台共用 API、组件库与令牌源。
- 移动端页面**独立设计**（单列、卡片、大触控目标、无密集表格、无多标签页 / 侧边栏 / 面包屑），不是 PC 页面的响应式缩窄。
- 适老化 = **移动端默认基线**：正文不小于 16px、触控目标不小于 44×44px、提高文字与控件边界的对比度、主操作整行大按钮吸底；经 `[data-mode='mobile']` 令牌作用域生效，**不做用户可切换的适老模式**。
- PC 后台不做适老化；PC 的视觉基线仍按 ADR-008 与 `product/平台布局.md`。
- 令牌仍是 `packages/tokens` 单一源，按端提供两套取值。

**后果**

- 手机浏览器即可开单，无小程序注册 / 审核链路；两端一套代码、一个部署单元。
- ADR-008「适老模式即切换另一套令牌」的落地口径收窄为「按端套用不同令牌」，不再承诺开关。
- 代价：移动端页面独立实现与维护；PC 与移动不共享布局代码，只共享组件、令牌与业务纯函数。

## ADR-012：多租户启用——登录确定租户、平台运营独立身份、跨租户受控作用域

- 状态：已采纳（2026-11-15）

**上下文**

- ADR-005 已复活，`tenant_id` 全表预留；但当前单租户恒为 `default`，请求上下文从未写入租户，`currentTenantId()` 以常量兜底。
- 第二个真实租户与对外销售计划已经成立，多租户前提从「预留」转为「启用」；若继续以 `default` 兜底，任何漏设上下文的代码都会静默读写首个租户，成为越权漏洞。
- 平台运营需要跨租户管理租户、套餐与功能，与租户内四角色的语义不同；共用账号表会让平台账号被计入某个租户的账号数，也可能误入业务权限。
- 不做白标与自定义域名，因此不能用子域名识别租户；租户标识必须在登录时确定。

**决策**

1. **登录确定租户**：租户用户登录输入租户编号 + 账号 + 密码；服务端先校验租户存在且启用，再在该租户作用域内校验账号；访问令牌与刷新令牌均携带 `tenantId`；请求上下文缺失租户即拒绝，取消 `default` 兜底。
2. **平台运营独立身份**：平台运营账号使用独立表、独立入口 `/ops/login`、独立令牌受众、独立守卫与平台 scope；不与租户 `users` 共表，不共用四角色。
3. **跨租户受控作用域**：只有 `tenant` 模块暴露 `runWithTenant(targetTenantId)`，且只在平台守卫之后调用；业务接口禁止从请求头、查询参数或请求体接受 `tenantId`；`tenants`、`plans`、`plan_features`、`tenant_features`、`platform_users`、`platform_event_logs` 等全局表排除租户过滤。
4. **编号与历史**：首个租户保留主键 `default`，登录编号取 `TN-00001`；之后新租户按 `TN-#####` 递增；租户编号创建后不可改、永不复用。
5. **功能与权限正交**：`feature` 是租户级开关（这个租户有没有买），`scope` 是用户级权限（这个人能不能操作）；校验顺序为登录 → 租户状态 → feature → scope。

**后果**

- 所有租户请求必须带租户上下文；seed、迁移与脚本需显式指定租户，否则报错。
- 平台运营成为第三端 `/ops`，仅 PC，不复用业务后台壳，不做移动适配。
- 需新增跨租户隔离、令牌互斥、租户停用即时生效、功能关闭返回 `FEATURE_DISABLED` 等测试。
- 数据仍单库单 schema，隔离靠 `tenant_id` 与数据访问层；不引入分库分表。
- 对外提供租户前必须完成域名与 HTTPS，技术方案 §9.5 的升级条件已触发。
- 代价：登录多一个字段；平台运营与租户用户两套身份需要分别维护；每个新增可售模块都要登记 feature。

## ADR-013：设计类功能的文档模型与导出边界

- 状态：已采纳（2026-11-17）

**上下文**

- 包装设计需要同时支持托盘、木箱、围板、垫木、钢带箱等多种单元；若每种单元各自拼 SVG、各自写导出，图纸、BOM 与报价口径会分裂。
- 图纸与 BOM 需要可复现、可测试、可版本化；服务端生成图形会引入字体、渲染器与部署依赖。
- 3D 只是设计的派生视图，不能成为数据源。

**决策**

1. **几何、图纸、BOM、报价、开料均为纯函数模型**，放 `packages/shared/src/design/`，不依赖 DOM、Three.js 或 Prisma。
2. **渲染与导出在客户端**：SVG / DXF / CSV / OBJ / STL 由浏览器生成，PDF 走浏览器打印；服务端只持久化数据、编号、版本与审计。
3. **3D 是派生视图**，消费同一份几何与 mesh 描述，不独立建模。
4. **图纸是图元文档**（图元 / 图层 / 图幅 / 图框 / 图号），SVG 与 DXF 是两个渲染器，消费同一份图元。

**后果**

- 图纸与页面所见一致；导出可单测、可快照；服务端无需图形依赖。
- 新增单元类型只加模板数据与构建器，不新增导出链。
- 代价：客户端需要承担计算与导出；超大图纸后续可能需要 Web Worker 或分页渲染。
