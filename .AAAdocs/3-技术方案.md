# 技术方案

***

## 1. 系统概述与架构

> 只描述**技术组件构成与职责边界**，不涉及任何业务功能。

### 1.1 技术组件全景

```
┌── 客户端层 ───────────────────────────────────────────┐
│  web（Next.js）        miniapp（Taro）      第三方/开放调用方 │
└──────────────────────────┬───────────────────────────┘
                           │ HTTP（统一业务 API）
┌── 服务层 ────────────────▼───────────────────────────┐
│  server：模块化单体（NestJS）                          │
│  ├ 业务模块 · 各自 Controller/Service/表              │
│  ├ 横切中间件：鉴权 · 审计 · 限流 · 错误处理           │
│  └ OpenAPI 契约（代码生成）                            │
└──────────┬───────────────────────────┬───────────────┘
           │ 内部接口/事件              │
           │                    ┌──────▼───────────────┐
           │                    │ agent 服务            │
           │                    │ MCP Server → 调业务API │
           │                    └──────────────────────┘
┌── 数据层 ─▼───────────────────────────────────────────┐
│  PostgreSQL（业务 + 向量）  Redis（缓存/队列）  S3对象存储 │
└───────────────────────────────────────────────────────┘
```

### 1.2 组件职责边界（硬规则）

| 组件            | 职责             | 硬边界                                |
| ------------- | -------------- | ---------------------------------- |
| web / miniapp | 展示与交互          | 只经统一 API 取数据；**不直连数据库**            |
| server        | 全部业务逻辑、数据读写、审计 | **唯一**访问数据库的进程                     |
| agent         | 对话理解、工具编排      | 只经 MCP → 业务 API；**不直连数据库**、不内嵌业务规则 |
| 数据库           | 数据持久化          | 只被 server 访问                       |

### 1.3 通信原则

- **人类流量**走统一业务 API（HTTP）；**Agent 流量**走 MCP → 同一套业务 API；两股客流在服务层汇合。

- 模块之间**只走公开接口/领域事件**，禁止跨模块穿透（详见 §4）。

- **三条全局禁令**：① 任何模块禁止直接读他模块的表；② 任何客户端与 Agent 禁止直连数据库；③ 密钥禁止出现在前端可见变量中。

## 2. 技术栈选型

| 层         | 选型                           | 作用                                 |
| --------- | ---------------------------- | ---------------------------------- |
| 语言        | TypeScript（`strict` 全开）      | 全栈统一语言，前后端与 Agent 共用类型，消除跨端类型错配    |
| 运行时       | Node.js LTS                  | 统一的 JS 运行时，承载 web / server / agent |
| 网站/后台     | Next.js（App Router）          | 面向人的界面（对客端 + 后台），SSR 兼顾对外 SEO      |
| 小程序       | Taro（跨端）                     | 移动端小程序外壳，一套代码出多端                   |
| 后端        | NestJS                       | 模块化单体宿主，模块机制即领域边界载体                |
| ORM       | Prisma                       | 数据访问层；schema 即表结构唯一事实源，改表走可追溯迁移    |
| 数据库       | PostgreSQL + pgvector        | 业务数据 + 向量共库存储                      |
| 缓存/队列     | Redis + BullMQ               | 缓存与异步任务队列                          |
| 对象存储      | S3 兼容                        | 图纸 / PDF / 照片等文件存储                 |
| 前端样式      | Tailwind CSS                 | 样式与设计令牌的载体                         |
| 前端组件      | shadcn/ui（源码入库）+ Radix       | 组件来源，源码入库、归仓库所有                    |
| 校验        | zod                          | 前后端共用的边界校验                         |
| Agent 运行时 | LangGraph.js / Vercel AI SDK | Agent 对话与工具编排，保持 TS                |
| Monorepo  | pnpm workspace + Turborepo   | 依赖链接与构建编排                          |
| 测试        | Vitest + Playwright          | 单测与 E2E                            |

**编码基线**：`strict` 全开；禁止滥用 `any`（必要时显式标注并说明理由）。

## 3. 仓库与目录结构

### 3.1 组织方式

单仓库 **monorepo**（pnpm workspace + Turborepo），不拆多仓库；仅 SaaS 开放第三方 SDK 时从本仓库发包，不拆仓库。

### 3.2 目录结构

```
mcc/
├── apps/
│   ├── web/                    # Next.js：对客端 + 管理后台
│   │   ├── app/
│   │   │   ├── (shop)/         # 对外路由组（可索引，SEO）
│   │   │   └── admin/          # 后台路由组（鉴权后进入）
│   │   ├── components/         # shadcn 组件源码（归本仓库）
│   │   └── .env.example        # 变量清单（进 git）
│   ├── miniapp/                # Taro 小程序
│   │   └── .env.example
│   ├── server/                 # NestJS 模块化单体（唯一后端）
│   │   ├── src/
│   │   │   ├── modules/        # 业务模块（每模块四件套，见 §4）
│   │   │   └── common/         # 鉴权/审计/限流/错误处理/契约生成
│   │   └── .env.example
│   └── agent/                  # Agent 服务（MCP Server + 对话逻辑）
│       └── .env.example
├── packages/
│   ├── db/                     # prisma/schema.prisma（表结构唯一定义）＋ Client 出口
│   ├── shared/                 # 共享类型 + zod + 类型化 API client
│   ├── tokens/                 # 设计令牌（web/miniapp 共用）
│   └── config/                 # tsconfig / eslint / tailwind 预设
├── docker-compose.yml          # 开发环境：PG + Redis
├── turbo.json
└── pnpm-workspace.yaml
```

### 3.3 各单元职责（一句话）

| 单元                | 职责                         |
| ----------------- | -------------------------- |
| `apps/web`        | 全部面向人的界面（对客端 + 后台），只消费 API |
| `apps/miniapp`    | 移动端小程序，只消费 API             |
| `apps/server`     | 全部业务逻辑与数据读写，唯一访问数据库者       |
| `apps/agent`      | 意图理解与工具编排，经 MCP 调 API      |
| `packages/db`     | 表结构的唯一定义，产出全仓库共享类型         |
| `packages/shared` | 跨端共享类型、校验、API client       |
| `packages/tokens` | 设计令牌定义与主题变量                |
| `packages/config` | 统一工程配置                     |

### 3.4 依赖方向（禁止反向）

```
web / miniapp / agent ──► packages/shared ──► packages/db
server ────────────────► packages/shared ──► packages/db
        （apps 之间禁止相互 import；apps 只依赖 packages）
```

**复用与结构**：类型、校验、client、令牌一律取自 `packages/*`；命名与目录遵循 §3、§4 模板，禁止自创结构。

## 4. 模块结构与边界规则

### 4.1 模块四件套模板

```
modules/<domain>/
├── <domain>.controller.ts   # 对外 HTTP 入口（API）
├── <domain>.service.ts      # 业务逻辑
├── dto/                     # 入参/出参类型（zod/class-validator）
├── <domain>.module.ts       # NestJS 模块声明
└── index.ts                 # ★ 唯一公开出口：显式导出供他模块使用
```

### 4.2 边界硬规则

1. **自有资产**：每个模块拥有自己的 Controller、Service、数据表；
2. **公开接口**：跨模块只能调用对方 `index.ts` 导出的内容，禁止直接读对方的表；
3. **禁止穿透**：禁止 import 对方内部实现（如 `../<domain>/<domain>.service`），只许 `../<domain>`（即 index）；
4. **数据所有权**：从首次建表起就必须清晰——每张表只属一个模块。

**强制手段**：eslint 边界规则（`eslint-plugin-boundaries` 或等价方案）在 CI 中拦截上述违规。

### 4.3 模块间通信

- **同步**：调用对方的公开 Service 接口；

- **异步**：发领域事件（记录到事件日志表），他模块按需消费；

- 禁止：跨模块直连数据库、跨模块共享可变状态。

## 5. 数据模型概览

> 只放通用设计约定；**完整表结构见** **`packages/db/prisma/schema.prisma`**，业务字段语义见产品文档。

### 5.1 概念关系（示意）

```
[业务实体A] ──1:N──► [业务实体B] ──1:N──► [业务实体C]
      ▲                                        │
      └────────── 领域事件日志（全局） ◄────────┘
```

（具体实体与基数以 schema 与产品文档为准。）

### 5.2 通用字段约定（全表适用）

| 约定                        | 说明                                 |
| ------------------------- | ---------------------------------- |
| 主键                        | 统一采用不可推测的全局唯一 ID（具体算法脚手架锁定）        |
| `created_at / updated_at` | 全表必备，UTC 存储                        |
| 软删除                       | 业务数据用 `deleted_at`，禁止物理删除（审计与恢复需要） |
| 金额/尺寸                     | 用精确数值类型（Decimal），**禁止浮点**          |
| 单位                        | 长度、重量统一基准单位存储，展示层换算                |

### 5.3 模式约定

- **状态机模式**：有生命周期的主实体（如订单）用显式状态字段 + 状态流转表，禁止在业务代码里散落 `if status ==`；

- **事件日志表**：全局记录领域事件（谁、何时、对什么、做了什么），供审计与未来新模块消费；

- **审计字段**：写操作记录操作者身份（含 Agent 的 service account）。

### 5.4 迁移纪律

- 只向前迁移；删列/改列走先加新列 → 双写/回填 → 切读 → 再删旧列；

- 迁移脚本先过 staging 再过 prod；

- **禁止修改已应用的历史迁移文件**。

## 6. API 契约规范

### 6.1 风格与生成

- REST 风格，全量契约由 NestJS 装饰器**代码生成** OpenAPI（ADR-006）→ 产出 `openapi.json` → 生成 `packages/shared` 中的类型化 client；

- **契约与实现永远同步**，禁止手写与实现脱节的接口文档。

### 6.2 命名与版本

| 项  | 约定                                                     |
| -- | ------------------------------------------------------ |
| 路径 | 资源小写复数、kebab-case：`/api/v1/quote-orders`               |
| 版本 | URL 中带主版本 `/api/v1`，仅破坏性变更升版                           |
| 动作 | 尽量用 HTTP 语义（GET/POST/PUT/PATCH/DELETE），非 CRUD 动作用子资源表达 |

### 6.3 请求约定

- 分页：统一 `page`/`pageSize`（或 cursor，二选一并全站一致）；

- 排序/过滤：统一查询参数命名，禁止各接口自定义；

- 幂等：会重复提交的写操作（如创建）支持 `Idempotency-Key` 请求头。

### 6.4 响应与错误

- 统一响应结构（成功 / 失败一致的外层）；

- 错误采用统一体（建议 RFC 7807 `application/problem+json`）：`code`（机器可读）+ `message`（中文人可读）+ `details`；

- 禁止把内部异常栈或数据库信息返回给调用方。

### 6.5 语义化纪律（契约可理解性）

- **枚举禁止魔法数字**：状态值用可读字符串或带 `description` 的枚举，不用 `3` 代表待发货；

- 每个字段的 `description` 写**业务语言**（如出材率：成品体积/原木体积），不写技术语言；

- **业务术语表**：维护在 `1-产品文档.md`（业务词 ↔ 系统字段 / 枚举），此处只引用不重述。

### 6.6 变更与废弃

- **只做增量变更**：加字段/加接口自由；破坏性变更走升版 + 双写过渡 + 显式废弃期；

- 废弃接口须标注并保留过渡期，禁止突然删除；

- 契约变更须人工过目（多端与 Agent 共用同一契约，改动面广）。

## 7. 前端规范

### 7.1 设计令牌（Design Tokens）

- 令牌定义于 `packages/tokens`，web 与 miniapp 共用**同一份源**；

- 令牌覆盖：颜色、字号、间距、圆角、触控目标尺寸、对比度；

- **禁止**在业务代码写死具体值（`#0FDC78`、`16px`），一律引用令牌（对应 ADR-008）。

### 7.2 组件库纪律

- 组件一律来自组件库（shadcn/ui，源码入库） + 令牌；

- 第三方组件库（如 antd）仅当局部复杂表格查询确需时**按需引入**，引入须记 changelog；

- 禁止裸写内联样式、禁止 `!important` 覆盖。

### 7.3 断点（响应式）

- 全站统一断点档位（如 `sm/md/lg/xl`），禁止页面各写各的判断；

- **移动优先**书写（默认移动端，向上覆盖）。

### 7.4 数据与状态

- 服务端状态统一走查询库（如 TanStack Query）管理缓存与失效，不用全局 store 硬存服务端数据；

## 8. 认证与安全

### 8.1 身份与凭证

| 主体             | 凭证方式                               |
| -------------- | ---------------------------------- |
| 人（web/miniapp） | 登录后签发访问令牌（短期）+ 刷新令牌（长期），全端统一       |

- 密码存储：强哈希（argon2 或等价方案），禁止可逆存储；

- 传输：全站 HTTPS。

### 8.2 权限模型

- **RBAC**：角色 → 权限（scope）；

- 权限校验统一在服务层守卫中完成，不在前端做安全判断。

### 8.3 密钥与环境变量规则

- git 中只保留 `.env.example`；真实 `.env` 一律 ignore；

- `.env` **按 app 分散持有**（`apps/web/.env.local`、`apps/server/.env`、`apps/agent/.env`）；

- **local** 用真实 `.env` 文件；**staging/prod** 用部署平台环境变量注入，**服务器上不落文件**；

- **红线**：前端框架中公开前缀变量（Next.js 的 `NEXT_PUBLIC_`）会打进浏览器包，**密钥绝不许加此前缀**；

- `.env` 相关 diff **一律人工过目**。

### 8.4 边界防护

- 所有外部输入在服务层边界用 zod 校验；

- 统一限流（按主体/接口），写入类与登录类重点防护；

- 敏感文件走**签名 URL + 私有读写**，禁止可猜测的公开路径。

### 8.5 审计

- 全量写操作记录审计日志（主体、时间、对象、动作、结果）；

- 审计日志不可篡改、只增。

## 9. 环境与部署

### 9.1 环境分层

| 环境      | 位置            | 数据库                | 用途            |
| ------- | ------------- | ------------------ | ------------- |
| local   | 本机            | Docker 起的 PG/Redis | 本地开发自测        |
| staging | 云服务器          | 独立测试库              | 真机验收（含小程序体验版） |
| prod    | 云服务器 + 托管 RDS | 正式库                | 真实数据          |

### 9.2 核心规则

- **区分环境的是配置不是代码**：代码只有一份（main），差异全在配置；

- 测试库与生产库**物理隔离**，绝不共用连接串；

- 配置载体见 §8.3（local 文件 / staging、prod 平台注入）。

### 9.3 部署

- 开发环境：`docker compose up` 起 PG + Redis；

- 生产：应用容器化部署，**数据库用托管 RDS**（自动备份、可回滚）；

- 发布流向：功能分支 → main → 自动部署 staging → 验收 → 打 tag → 部署 prod（单向）。

### 9.4 迁移与发布纪律

- 迁移只向前，先 staging 后 prod（详见 §5.4）；

- 生产数据进测试环境必须**脱敏**。

| 层次     | 范围                                  | 工具                    |
