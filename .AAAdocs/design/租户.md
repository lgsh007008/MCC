# 租户领域实现设计（tenant）

> 定位：租户领域的**实现设计**（How）。需求见 `product/租户.md`（R-租户-001 / R-租户-002 / R-租户-003）。
> 全局约定见技术方案 §4（模块边界）/ §5（数据模型）/ §6（API 契约）/ §8（认证与安全），本文件只写本领域落点，不重述约定。

---

## 1. 模块结构与职责

`modules/tenant` 为平台领域模块，遵循技术方案 §4.1 四件套模板：

```
modules/tenant/
├── tenant.controller.ts    # 租户列表 / 详情 / 开通 / 更新 / 启停 / 改套餐 / 功能覆盖
├── plan.controller.ts      # 套餐列表 / 新建 / 更新 / 启停
├── tenant.service.ts       # 编号生成、开通、启停、套餐与覆盖、有效功能解析
├── tenant-context.ts       # runWithTenant：受控跨租户作用域
├── dto/                    # 契约形状（@nestjs/swagger class）；运行时校验用 @mcc/shared 的 zod schema
├── tenant.module.ts
└── index.ts                # 唯一公开出口
```

- `tenants` / `plans` / `plan_features` / `tenant_features` 四张**全局表**归本模块（数据所有权，技术方案 §4.2）。
- 本模块**不读写任何业务表**，不导入 auth / order / production 等模块；账号数与管理员账号经 auth 的公开接口由前端组合，平台审计由 audit 的拦截器记录。
- **单向依赖**：auth 导入 tenant（登录解析租户、额度、功能判定）；tenant 不导入 auth。开通首管理员由前端两步编排（先建租户，再调 auth 建管理员），避免双向依赖与循环。
- `runWithTenant` 只在平台守卫之后由本模块内部或平台页面调用；业务接口不得接受外部传入的 `tenantId`。

## 2. 数据模型概览

> 细节归 `packages/db/prisma/schema.prisma`（表结构唯一事实源，技术方案 §5），此处只列概览与约定。

| 表 | 字段要点 | 备注 |
| --- | --- | --- |
| `tenants` | 编号（唯一）、名称、套餐 id、状态、`session_epoch`、备注 | 全局表，无 `tenant_id`；首个租户主键保留 `default`、编号 `TN-00001`；`code` 唯一；`plan_id` 外键 `RESTRICT` |
| `plans` | 名称（唯一）、账号额度、状态、备注 | 全局表；不设价格、账期与计费字段；不可删除，只可停用 |
| `plan_features` | 套餐 id + 功能标识 | 全局表；联合主键 `(plan_id, feature_code)` |
| `tenant_features` | 租户 id + 功能标识 + 启用标记 | 全局表；**只存与套餐不同的覆盖项**；联合主键 `(tenant_id, feature_code)` |

- 枚举：`tenant_status` = `active` / `suspended`；`plan_status` = `active` / `inactive`。
- `session_epoch`：整数、默认 0；停用租户时 +1。auth 的访问令牌与刷新令牌携带签发时的 epoch，守卫与刷新校验不一致即拒绝。这样无需 tenant 反向调用 auth 删除令牌，也能保证「停用后旧令牌不恢复」。
- **全局表排除租户过滤**：`Tenant`、`Plan`、`PlanFeature`、`TenantFeature`、`PlatformUser`、`PlatformRefreshToken`、`PlatformEventLog` 必须从 `common/prisma-tenant.extension.ts` 的 `$allModels` 钩子中排除；否则租户注册表会被当前租户条件过滤。
- `currentTenantId()` **取消 `default` 兜底**：租户作用域缺失时抛错。seed、迁移脚本、平台开通流程必须显式 `runWithTenant`；全局表访问不需要租户上下文。
- **去掉数据库默认值**：所有业务表的 `tenant_id` 移除数据库默认值；现有行已是 `default`，不需要回填。新插入由数据访问层强制落当前租户，漏设上下文即失败，避免静默写入首租户。
- 有效功能不落库、实时解析；租户与套餐变更后即时生效。

## 3. 有效功能与额度（纯函数，`packages/shared`）

- 功能清单集中在共享常量 `FEATURE_CATALOG`，分两类：
  - **基础功能**：`account`、`platform`、`tenant`，永远启用，不参与套餐配置；
  - **可售功能**：`order`、`customer`、`purchase`、`supplier`、`production`、`finance`、`audit`。
- `resolveEffectiveFeatures(planFeatures, overrides)`：
  1. 先并入全部基础功能；
  2. 并入套餐功能；
  3. 应用租户覆盖：`enabled = true` 加入，`enabled = false` 移除；
  4. 基础功能不可被覆盖移除；
  5. 输出去重、稳定排序的功能标识数组。
- `isOverQuota(accountCount, maxAccounts)`：账号数 > 额度即超额；额度口径为未删除账号数（含停用），平台运营账号不计入。新建账号前按「当前账号数 + 1」预判（`isOverQuota(accountCount + 1, maxAccounts)`），等于额度时即拒绝。
- `normalizeOverrides(planFeatures, overrides)`：覆盖值与套餐一致时删除该覆盖项，保证 `tenant_features` 只存真正的偏差。
- 增删改功能或套餐后，失效 Redis 键 `tenant:features:{tenantId}`（TTL 60 秒兜底），下一次请求重新解析。
- 纯函数单测为最高优先级；`tenant.calc.ts` 纳入技术方案 §10 的覆盖率硬门槛。

## 4. 编号生成

- 租户编号 `TN-#####`：事务内取 `TN-` 前缀最大流水 +1，唯一约束兜底并发冲突（P2002 重试）。
- 首个租户由迁移写入 `id = default`、`code = TN-00001`；之后新租户使用数据库默认主键与递增编号。
- 编号创建后不可改、永不复用；租户不删除，因此不存在回收问题。
- 套餐不设业务编号，以唯一名称识别。

## 5. 接口清单

> 契约由 NestJS 装饰器代码生成 OpenAPI（技术方案 §6.1 / ADR-006），本文不手写参数与响应细节，只列清单。

| 接口 | 路径 | 用途 |
| --- | --- | --- |
| tenants-list | `GET /api/v1/ops/tenants` | 租户列表（筛选：编号 / 名称模糊、状态、套餐；排序：创建日期；分页）；不含账号数，账号数由 auth 批量接口前端组合 |
| tenant-detail | `GET /api/v1/ops/tenants/:id` | 租户详情（含套餐、覆盖项、有效功能；不含账号数） |
| tenant-create | `POST /api/v1/ops/tenants` | 开通租户（名称、套餐、备注；编号自动生成；**只建租户，不建管理员**） |
| tenant-update | `PUT /api/v1/ops/tenants/:id` | 更新名称与备注 |
| tenant-status | `PATCH /api/v1/ops/tenants/:id/status` | 停用 / 启用；停用时 `session_epoch + 1` |
| tenant-plan | `PUT /api/v1/ops/tenants/:id/plan` | 改套餐；返回套餐功能与额度变化，不返回账号数 |
| tenant-features | `PUT /api/v1/ops/tenants/:id/features` | 全量提交覆盖项（只含与套餐不同的项）；返回有效功能 |
| plans-list | `GET /api/v1/ops/plans` | 套餐列表（含租户使用数） |
| plan-create | `POST /api/v1/ops/plans` | 新建套餐（名称、功能集合、账号额度、备注） |
| plan-update | `PUT /api/v1/ops/plans/:id` | 更新套餐 |
| plan-status | `PATCH /api/v1/ops/plans/:id/status` | 停用 / 启用套餐；停用后不可被新租户选择 |

- 全部要求平台 scope：查看 `platform:tenant:view`；写操作 `platform:tenant:manage`。
- **跨模块引用**（定义在 `design/账号与权限.md`，本域只引用）：
  - `GET /api/v1/ops/tenant-account-counts?tenantIds=`：批量账号数；
  - `GET /api/v1/ops/tenants/:tenantId/admins`：租户管理员账号列表；
  - `POST /api/v1/ops/tenants/:tenantId/admins`：补建 / 新增租户管理员；
  - `POST /api/v1/ops/tenants/:tenantId/admins/:userId/reset-password`：重置租户管理员密码。

**公开接口**（供 auth 与平台守卫使用，经 `index.ts` 导出）：

- `findByCode(code)`：按登录编号取租户（全局表，不过滤租户）；
- `findById(id)`：取租户基本信息；
- `assertActiveById(id)`：校验租户存在且启用，返回租户；
- `getQuota(tenantId)`：返回套餐账号额度；
- `getEffectiveFeatures(tenantId)`：返回有效功能数组（带短缓存）；
- `assertFeature(tenantId, featureCode)`：不可用即抛 `FEATURE_DISABLED`；
- `runWithTenant(tenantId, fn)`：在指定租户作用域内执行，供平台开通 / 平台守卫后使用。

## 6. 开通、启停与套餐流程

### 6.1 开通（两步）

1. 前端调用 `POST /api/v1/ops/tenants`：创建租户，返回 `id` 与 `code`；
2. 前端调用 auth 的 `POST /api/v1/ops/tenants/:tenantId/admins`：创建首管理员（账号、初始密码、`ADMIN`），auth 在该租户作用域内校验额度并写入；
3. 若第 2 步失败：租户保留，详情页显示「未创建管理员」，提供「补建管理员」入口；补建成功前该租户无账号、无法登录；
4. 开通成功进入租户详情，不弹成功回执。

- 第 1 步支持 `Idempotency-Key`；重复提交返回首请求结果。
- 不在 tenant 事务内跨模块创建管理员，避免 tenant ↔ auth 双向依赖。

### 6.2 启停

- 停用：`status = suspended`、`session_epoch + 1`、失效功能缓存；返回成功。
- 启停即时生效：auth 守卫每次请求校验租户状态与 epoch；刷新令牌校验 epoch，旧令牌不恢复；访问令牌最长 15 分钟过期。
- 启用：`status = active`，不重置 epoch；旧令牌仍无效，账号需重新登录。
- 停用不删数据、不清功能覆盖；启停均记录平台审计。

### 6.3 改套餐与功能覆盖

- 改套餐：校验目标套餐为启用态；更新 `plan_id`；失效功能缓存；返回新旧功能差异与额度变化。
- 功能覆盖：请求体为覆盖项数组；后端校验功能标识属于可售清单、基础功能不可覆盖；与套餐一致的覆盖项自动删除；保存后失效缓存。
- 降套餐不阻断：账号数由 auth 在新建账号时按目标额度校验；现有账号不强制停用。
- 套餐停用：不影响存量租户；新租户不可选择；列表返回使用该套餐的租户数供运营判断。

## 7. 前端实现节（web）

- **路由**（`app/ops/`，壳与菜单归 `design/平台布局.md`）：
  - `/ops/tenants` 租户列表；`/ops/tenants/new` 开通表单；`/ops/tenants/[id]` 详情；
  - `/ops/plans` 套餐列表。
- **列表页**：筛选 / 排序 / 分页按平台列表页模式；列 = 编号、名称、套餐、状态、账号数 / 额度、创建日期；行操作 = 查看 / 编辑 / 停用（启用）；改套餐与功能开关在详情页操作区。
- **账号数组合取数**：租户列表与详情并发调用 tenant 接口与 auth 的 `tenant-account-counts`，客户端按租户 id 合并；失败时显示 `--`，不阻断租户列表；不设置客户端排序与全量分页例外。
- **开通表单页**：`PageFrame`；字段 = 名称、套餐、备注、首管理员账号、初始密码；提交按两步执行——建租户成功后调 auth 建管理员；第二步失败时跳转详情并显示「未创建管理员」提示与「补建管理员」按钮。
- **详情页**：`PageFrame`；信息条 = 编号、套餐、状态、账号数 / 额度、创建日期、备注；功能区 = 有效功能摘要 + 「功能开关」弹窗；管理员账号区 = auth 提供的 `ADMIN` 列表（账号、状态）+「重置密码」；操作区 = 编辑 / 改套餐 / 停用（启用）/ 返回列表。
- **套餐页**：列表 + 新建 / 编辑弹窗（名称、功能多选、账号额度、备注）；行操作 = 编辑 / 停用（启用）；功能多选只列可售功能，基础功能不在选项中。
- **查询键**：`['ops-tenants', page, filters]`、`['ops-tenant', id]`、`['ops-plans']`、`['ops-tenant-account-counts', tenantIds]`、`['ops-tenant-admins', tenantId]`；写后按资源域失效。
- **共享件**：页面骨架用 `PageFrame`；列表、弹窗、确认框、日期与下拉全部复用 `components/ui`，不新增页面级样式。
- 页面不出现租户业务数据，不提供代登录入口。

## 8. 与其他领域的边界

- **auth**：auth → tenant 单向依赖。auth 登录按 `findByCode` 解析租户、按 `getQuota` 校验额度、按 `getEffectiveFeatures` 判定功能；tenant 不导入 auth。租户管理员账号与账号数归 auth，tenant 页面只经公开接口引用。
- **audit**：平台租户操作由 audit 的 `platform_event_logs` 记录；tenant 不写审计表、不导入 audit。
- **platform**：`/ops` 壳、菜单、登录分流归 platform；tenant 只提供页面内容与菜单项归属。
- **order / production**：业务模块的功能闸门由 common 的 `FeatureGuard` 调用 tenant 公开接口完成；销售单详情的材料毛利卡由 `production` 功能控制，tenant 不感知具体页面。
- **禁止**：tenant 直读业务表；业务接口接受外部 `tenantId`；平台页面代登录租户账号。

## 9. 迁移与 seed

1. 新建 `tenants`、`plans`、`plan_features`、`tenant_features` 四张全局表与索引；
2. 写入首个租户：`id = default`、`code = TN-00001`、名称「梅好木业」、套餐「标准版」；
3. 写入标准版套餐：包含当前全部可售功能（order / customer / purchase / supplier / production / finance / audit），账号额度取实现常量（初始 20，可在套餐页调整），状态启用；套餐主键必须是合法 UUID（接口 schema 用 `z.uuid()` 校验，非版本化 UUID 会被 400 拒绝）；
4. 移除全部业务表 `tenant_id` 的数据库默认值；
5. 更新 seed：先写全局表，再创建现有管理员与基础数据；seed 使用未扩展的原始 PrismaClient，不经租户扩展，业务表写入显式带 `tenant_id`；
6. 平台运营账号由 seed 单独写入 `platform_users`（不属于任何租户）；
7. 迁移不重写历史行；现有 `tenant_id = default` 保持不动；
8. 迁移后重建 Prisma Client、OpenAPI 与 web client。

## 10. 测试

- **共享纯函数**：基础功能永远启用、套餐与覆盖的增删、覆盖与套餐一致时归一、额度判断、空套餐。
- **服务端集成**：租户开通 / 列表 / 详情 / 启停 / 改套餐 / 功能覆盖；停用后 epoch 失效；套餐停用不影响存量；全局表不受租户过滤；跨租户读写互相不可见；平台 token 与租户 token 互斥；额度超限拒绝；功能关闭返回 `FEATURE_DISABLED`。集成测试使用独立租户 `TN-90001`（`apps/server/test/setup.ts` 创建并在每个 spec 前清空该租户业务数据），与演示 / 正式数据隔离，避免库存期初与账号额度相互影响。
- **前端 E2E**：平台登录 → 开通租户 → 补建管理员 → 配置功能 → 租户登录看到对应菜单 → 关闭功能后菜单消失且接口 403 → 停用后无法登录 → 平台审计可见操作；表单 / 详情页通过 `expectPageFrame` 骨架断言。
