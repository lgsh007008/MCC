
## 文档体系与优先级

**四层文档**：产品文档、ADR、技术方案、模块设计文档。

```
.AAAdocs/
├── 0-文档驱动开发机制.md            # 本文件（元文档 ＋ 需求开发流程 SOP）
├── 1-产品文档.md                    # 产品总纲（What：全局）
├── 2-adr.md                         # 架构决策记录（Why：只增不改）
├── 3-技术方案.md                     # 技术方案（How：全局）
├── product/<领域>.md                # 各领域需求（与 design 同名配对）
├── design/<领域>.md                 # 各领域实现设计（与 product 同名配对）
```


**优先级（冲突时以此裁决）**

```
产品文档（What/Why，需求与约束）
      ↑ 引用（R-xxx-NNN）
ADR  >  技术方案（全局约定）  >  模块设计文档（领域实现）
```

**说明**：ADR 最高；技术方案是其执行展开，并约束所有模块设计文档；各文档均自洽完整，不依赖任何外部讨论记录。

## 三条铁律

1. **正文只放当前真相**（现在是什么样），历史脉络走文末 changelog；
2. **单一事实源**：每条信息只在一处定义，他处只引用不复制（复制必漂移）；
3. **文档只放约定与指针**：技术细节（表结构、接口、AI 行为规则等）由代码或生成物承载，文档不重复定义，只写**概览 + 约定 + 详见 XX**

## 变更机制

本节机制对本文档体系下的**所有文档**均适用，所有文档都必须遵守。

新增、修改或删除决策 → 先更新对应文档的相应章节 → 在该文档 changelog 末尾**追加一行**（列：位置 / 类型 / 原本 / 现在 / 原因；类型仅取「新增」「修改」「删除」）。

**版本小节命名格式**：`v<YYYYMMDD>`，如 `v20261015`。同一天只对应一个小节，新的一天即新的版本小节。

**纪律**：changelog 只增不改——已写入的历史行**不得修改**，变更只能新增：跨天在文末**追加新的版本小节**，同一天则在当日小节内末尾**追加新行**。

## 文档定位

### 产品文档

- **回答**：What/Why——需求、约束、验收标准、**页面设计**。
- **位置与拆分**：`1-产品文档.md` 为全局总纲；各领域需求在 `product/<领域>.md`，与 `design/<领域>.md` 同名配对。
- **关键规则**：需求编号 `R-xxx-NNN` 在此定义，供他文档引用；业务结构（领域地图 / 模块清单）与领域划分方法在总纲维护。

### ADR

- **回答**：为什么定死——不可逆的架构决策。
- **位置与拆分**：`2-adr.md` 单文件，按 `ADR-NNN` 分节。
- **关键规则**：只增不改——决策被取代时新增新条，不回头改旧条；优先级最高，冲突时以此裁决；每条自洽完整，不依赖外部讨论记录。

### 技术方案

- **回答**：全局怎么做——跨模块的约定、边界、规范。
- **位置与拆分**：`3-技术方案.md` 单文件。
- **关键规则**：全局约定的唯一出处，被所有模块设计文档引用。

### 模块设计文档

- **回答**：该领域具体怎么做——表结构、接口清单、状态机、算法与关键流程。
- **位置与拆分**：`design/<领域>.md`，**每领域一份**，与 `product/<领域>.md` 同名配对；主体为**后端**设计（数据模型细节、接口清单、状态机、算法与关键流程），另含**前端实现节**。
- **关键规则**：需求是改它的动作，不是它的单位——一个需求通常只更新一份（跨模块时更新多份），**不新增文件**；该领域**第一个真实需求**到来时创建，**不预生成空模板**。

## 前端与页面内容的归属

### 页面设计（属产品文档）

- 页面设计（这一页要有什么、怎么排、怎么交互）**归产品文档**（`product/<领域>.md`），作为对应需求的一部分——需求改则页面随之改，天然同步。
- 与前端实现的区别：页面设计=设计意图（人写，属 What）；前端实现=技术落地（AI 写，属 How）。

### 前端实现节（属模块设计文档）

本领域在**前端侧的技术落地设计**——回答前端代码怎么组织，而不是页面长什么样；它是页面设计（产品文档）与前端规范（技术方案 §7）之间的翻译层。**只在存在非平凡前端逻辑时写**（纯 CRUD 页面用现成组件拼即可，不为它单开一节）。

**应写（6 项）**

1. **页面 / 组件清单**——本领域涉及哪些页面与组件（报价页、报价结果页、报价列表…）；
2. **数据来源**——每个页面调哪些接口（引用本领域接口清单）、取数时机（服务端渲染 / 客户端请求）；
3. **客户端状态**——本领域特有的前端状态（报价草稿、多步表单中间态、未提交的编辑）；
4. **交互逻辑**——非平凡交互（实时联动刷新总价、防重复提交、错误提示与回退）；
5. **组件复用**——用哪些已有组件、是否需新增（受技术方案 §7 纪律约束）；
6. **可见性与权限**——哪些元素按角色 / 身份隐藏或禁用。

**不写（防越界）**

- 颜色 / 字号 / 间距 → 令牌（技术方案 §7）；
- 这页有哪些字段、怎么排 → 页面设计（产品文档）；
- 接口定义 → 本领域接口清单（模块设计文档的后端部分）。

### 跨模块页面（归属与接口引用）

- **页面归属唯一**：一个页面必须且只能归属一个领域——判定看它**围绕哪个实体 / 业务动作**展开（如订单详情页虽展示报价与生产信息，主实体是订单，归 `order`）；拿不准时用**变更检验**（该页面会随哪个领域的需求变化而改）。**一个页面只能在一份文档里被描述**，禁止两份各写一半（否则即成两份真相）。
- **接口引用可跨模块**：数据来源项列出该页面调用的**所有**接口并标注归属领域，**只引用、不重述定义**（定义留在各领域的接口清单）。
- **数据聚合**：优先**客户端并发调用 + 客户端组合**；聚合逻辑复杂或需权限裁剪时，由**页面所属领域**提供**只读聚合接口**，内部只调其他领域的公开接口。
- **禁止**：新建聚合模块直接读他领域的表——属边界穿透，违反 ADR-001。


## 需求开发流程（SOP）

> **用途**：把一个**具体需求**从提需求走到收尾——逐步执行、逐步停下确认。
> **发起**：本流程**由人工发起**，不自动启用；未经人工发起不得进入本流程。
> **落点**：改 `product/<领域>.md`、`design/<领域>.md`，必要时动 `1-产品文档.md`。

**停顿点规则（本流程通用，5 个停顿点一律不许豁免）**

1. 只出提案（改哪份文件 / 哪一节 / 改成什么 / 配哪条 changelog），不落笔；
2. 出完提案**立即停下**，等人工明确确认；
3. 未获**明确确认**（确认 / 可以 / 继续一类）前，禁止改任何文件、禁止进入下一步；
4. **含糊回复或沉默一律视为未确认**；
5. 禁止一次跨过多个停顿点，禁止一次改多份文档。

### 第 1 步 · 备料（不改文件）

- 读全四份全局文档：`0-文档驱动开发机制.md`（本文件）、`1-产品文档.md`、`2-adr.md`、`3-技术方案.md`；
- 再读本领域分册：`product/<领域>.md`、`design/<领域>.md`（若已存在）；
- **再读该领域现状代码**：该领域在 `apps/`、`packages/` 下的现有实现（按技术方案约定的目录定位，不硬编码路径）；`packages/db` 的 schema；已有的共享类型 / 令牌 / 组件；该领域已有测试代码的位置。

**目的**：先知道现状是什么。**没读过的代码不许写进设计与引用**。

### 第 2 步 · 定归属与范围 → 停顿点 1

输出五项判定，等确认。

| 判定 | 依据 | 结论影响 |
| --- | --- | --- |
| 属哪个领域 | 围绕哪个主实体 / 业务动作展开；拿不准用变更检验 | 决定改哪份分册 |
| 是否跨模块 | 会不会调其他领域接口、改其他领域页面 | 决定要更新几份文档 |
| 是否首个需求 | 该领域是否已有 `product/` 与 `design/` 两份分册 | 首个才创建（同名配对），否则只改 |
| 是否触及全局口径 | 是否改变全局规则 / 总纲 | 是 → 动 `1-产品文档.md` |
| 是否触及架构 | 是否需要不可逆的新决策 | 是 → 停下转 ADR 流程，不自行拍板 |

> 判定方法的完整口径（主实体判定 / 变更检验）见 `1-产品文档.md` 领域地图章节，此处只列判定项。

### 第 3 步 · 写需求 → 停顿点 2

- **改哪**：`product/<领域>.md`；
- **产出**：一个需求条目，字段见附则一；
- 出草稿 → **停顿点 2** → 确认后写入。

**自检**：编号唯一（`R-<领域>-NNN`，如 `R-订单-007`）；验收标准逐条可判定；不含战略 / 商业 / 竞品内容；页面设计只归属一个领域；未复制他文档内容，一律引用。

### 第 4 步 · 写实现设计 → 停顿点 3

- **改哪**：`design/<领域>.md`；
- **产出**（字段见附则一）：数据模型（**先读** schema 核对现状再引用，不复制表结构）、接口清单（**先读**已有实现与代码生成的 OpenAPI 再列；跨模块接口只引用他领域）、状态机 / 流程、算法、前端实现节（**仅非平凡前端逻辑时写**，按 6 项）、验收指针（测试代码路径 ＋ 结论位）；
- 出草稿 → **停顿点 3** → 确认后写入。

**自检**：未复制全局约定；表结构只引用 schema；未引入架构决策（有 → 转 ADR 出口）；前端实现节只写 6 项、不写样式 / 排布 / 接口定义；引用的 schema / 接口 / 已有类型，均已读过对应代码。

### 第 5 步 · 测试与验收 → 停顿点 4

- 逐条对照**验收标准**验收；先读（必要时运行）承载用例的**测试代码本体**，再下结论；用例不进文档；
- 验收指针里的测试代码路径必须是读到的**真实路径**；该领域无测试代码时，结论记**未覆盖**；
- 结论写入 `design/<领域>.md` 的**验收指针**：通过 / 例外 / 未覆盖；
- 回退：实现问题 → 回第 4 步；验收标准本身有误 → 回第 3 步并记 changelog；
- 出逐条结论 → **停顿点 4** → 确认后写入。

### 第 6 步 · 收尾 → 停顿点 5

- 每份被改文档按本文件**变更机制**在 changelog 追加一行（位置 / 类型 / 原本 / 现在 / 原因）；
- 跑附则三的收尾检查清单；
- 出拟追加行 ＋ 清单结果 → **停顿点 5** → 确认后写入。

### 附则一 · 字段模板

**需求条目（`product/<领域>.md`）**

```
### R-<领域>-NNN <需求标题>

- 背景 / 目的：（为什么做）
- 功能描述：（做什么）
- 约束与边界：（不能做什么、限制条件）
- 验收标准：
  1. （逐条可判定）
- 页面设计：（这页要有什么字段、怎么排、怎么交互；不涉及页面则写 无）
- 跨模块引用：（要调的其他领域接口，只引用不重述）
```

**设计条目（`design/<领域>.md`）**

```
### R-<领域>-NNN <需求标题> · 实现设计

- 数据模型：（引用 packages/db 的 schema，不复制）
- 接口清单：（本领域接口；跨模块接口只引用他领域）
- 状态机 / 流程：
- 算法：
- 前端实现节：（仅非平凡前端逻辑时写，按 6 项）
- 验收指针：测试代码路径；结论（通过 / 例外 / 未覆盖）
```

### 附则二 · 写码阶段纪律

- **读码前置**：改任何文件前先读该文件本身与相邻调用方，禁止凭记忆或推测改码；
- **方案预审**：实现前先列方案与取舍，确认后再写码（即停顿点规则的提案 → 确认 → 落笔）；
- **重组件闸**：新增任何重组件（缓存 / 队列 / API 网关 / 搜索服务 / 独立 Worker 等）之前必须**单独提出确认**，不得随普通需求顺带引入；
- **diff review**：每次生成后，对照技术方案的边界纪律与各步自检清单逐条检查；
- **人工过目**：涉及 `.env`、API 契约、数据库迁移的改动，一律停下交人工确认。

### 附则三 · 收尾检查清单

- [ ] 单一事实源：无内容复制，只有引用
- [ ] 需求编号跨文档引用一致（`R-<领域>-NNN`）
- [ ] 只写本领域特有内容，全局约定不重复
- [ ] changelog 已按变更机制追加（位置 / 类型 / 原本 / 现在 / 原因）
- [ ] 正文无英文双引号
- [ ] 文档文件名不带日期版本号

### 附则四 · 边界情形

1. **首个需求** → 先创建 `product/<领域>.md` 与 `design/<领域>.md`（同名配对），再按第 3 步起走；
2. **需求变更** → 改原条目，不新增文件；验收标准随之改、测试重跑；
3. **需求作废** → 从正文移除该条目（正文只放当前真相），changelog 记一行（类型：删除）；
4. **跨模块需求** → 更新多份 `design/`；接口只引用不重述；禁止新建聚合模块直接读他领域的表；
5. **需要不可逆决策** → 出本流程，新增一条 ADR（编号递增、作废号不复用）。
