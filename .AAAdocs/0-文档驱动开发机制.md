
## 文档体系与优先级

**四层文档**：产品文档、ADR、技术方案、模块设计文档。

```
.AAAdocs/
├── 0-文档驱动开发机制.md            # 本文件（元文档 ＋ 需求开发流程 SOP）
├── 1-产品文档.md                    # 产品总纲（What：全局）
├── 2-adr.md                         # 架构决策记录（Why：只增不改）
├── 3-技术方案.md                     # 技术方案（How：全局）
├── product/<领域>.md                # 各领域需求（与 design 同名配对）
├── design/<领域>.md                 # 各领域实现设计（与 product 同名配对）
├── archive/changelog/               # changelog 历史归档（只读，不参与配对与编号）
├── mock/                            # 交互原型（输入资产，不参与配对/编号/changelog）
├── 参考/                             # 竞品与行业工具 HTML（输入资产，同上）
```

> 根目录 `.战略与经营/` 收纳**经营与战略层档案**（业务调研、商业计划、阶段构想），与开发文档体系分置：不适用本文档的领域配对、需求编号与 changelog 机制。该目录内的叙事（含新业务方向构想）落地为真实需求时，按总纲领域地图规则在 `product/` 登记，才进入本文档体系。

> `mock/` 与 `参考/` 是设计输入资产（交互原型、竞品与行业工具 HTML），不是开发文档：不适用 product/design 配对、需求编号与 changelog 机制；其中的结论落地为真实需求时写入 product/design，原文件保持只读参考。


**优先级（冲突时以此裁决）**

```
产品文档（What/Why，需求与约束）
ADR  >  技术方案（全局约定）  >  模块设计文档（领域实现）
```

**说明**：ADR 最高；技术方案是其执行展开，并约束所有模块设计文档；各文档均自洽完整，不依赖任何外部讨论记录。

## 三条铁律

1. **正文只放当前真相**（现在是什么样），历史脉络走文末 changelog；
2. **单一事实源**：每条信息只在一处定义，他处只引用不复制（复制必漂移）；
3. **文档只放约定与指针**：技术细节（表结构、接口、AI 行为规则等）由代码或生成物承载，文档不重复定义，只写**概览 + 约定 + 详见 XX**

**单一事实源的分层**：同一事实只在一处定义——ADR 定义决策与理由，产品文档定义需求与页面，技术方案定义跨模块技术约定，`packages/tokens` 与代码定义取值与实现，design 定义本域落点。其他文档允许一句摘要 + 指针，禁止复制具体数值、规则清单与实现步骤。ADR 正文是决策时点的快照，不随现行口径更新；决策变化时新增 ADR 取代，不改旧条。

## 文档变更机制

本节机制对 0/1/2/3 与 product/design 下的**所有开发文档**均适用；mock/ 与 参考/ 是输入资产，不适用本节。

新增、修改或删除决策 → 先更新对应文档的相应章节 → 在该文档 changelog 末尾**追加一行**（列：位置 / 类型 / 原本 / 现在 / 原因；类型仅取「新增」「修改」「删除」）。

**版本小节命名格式**：`v<YYYYMMDD>`，如 `v20261015`。同一天只对应一个小节，新的一天即新的版本小节。也是在末尾增加。

**纪律**：changelog 只增不改——已写入的历史行**不得修改**，变更只能新增：跨天在文末**追加新的版本小节**，同一天则在当日小节内末尾**追加新行**。

## Changelog 归档

> 归档是唯一允许把已写入行移出活跃文档的动作；移出后行仍在归档文件中，changelog 只增不改的纪律不变。

### 目标与不变式

- **历史不丢**：移出的每一行必须原样存在于归档文件；校验器同时检查活跃区与归档区。
- **活跃区有界**：每份文档的活跃 changelog 以 12 个版本小节、20,000 字符为保留窗口；单节超限例外见下。
- **单一入口**：活跃文档只留指针，不写归档摘要，避免第二份真相。
- **归档只读**：归档文件只允许追加，不允许修改、重排或再搬回活跃区。

### 触发与保留窗口

- **版本小节**：`## Changelog` 下由 `### vYYYYMMDD` 开头、到下一个版本小节或文件末尾的整块内容。
- **触发条件**：版本小节数超过 12，或 changelog 区域字符数超过 20,000（按 Unicode 字符计，不按 UTF-8 字节）。
- **保留窗口**：从最旧的版本小节开始移出，直到满足上述两个条件；至少保留最新 1 节。
- **单节例外**：若只剩最新 1 节且仍超过字符上限，允许保留（不拆分单节），校验器给出警告；下一次变更新增小节后，旧节按正常规则归档。
- **执行时机**：需求开发流程第 8 步收尾时检查；归档作为独立维护动作执行，不混在业务变更里。

### 归档目录与文件格式

目录按来源文档镜像，按年份拆分：

```
.AAAdocs/archive/changelog/<原文档路径>/<年份>.md
```

如 `archive/changelog/3-技术方案/2026.md`、`archive/changelog/<领域>/<文档>/2026.md`。

归档文件不带 `## Changelog` 标题，头部只写来源与只读声明：

```markdown
# 3-技术方案 · Changelog 归档（2026）

> 来源文档：.AAAdocs/3-技术方案.md
> 本文件为只读历史记录，不参与现行需求编号、文档配对与 changelog 增量校验。
> 只允许按时间顺序追加从来源文档移出的版本小节，不允许修改已有内容。

### v20261015
...
```

### 活跃文档指针

在活跃文档 `## Changelog` 标题下第一行写指针；指针必须是可解析的 Markdown 链接，不能只写反引号路径：

```markdown
> 历史变更（v20261015）见 [archive/changelog/3-技术方案/2026.md](./archive/changelog/3-技术方案/2026.md)。本文件保留最近 12 个版本小节。
```

子目录文档用相对路径（如 `../archive/changelog/<领域>/<文档>/2026.md`）；跨年时列出多个归档文件。

### 搬移规则

- 整节搬移，原文照搬；不重排、不改写、不重新编号。
- 跨年按版本日期拆到对应年份文件，同一文件内保持时间顺序。
- 归档文件只允许追加；后续归档的节日期晚于归档中已有节，追加到末尾。
- 文档改名时归档目录随文档路径同步改名，归档内容不动；文档删除时先记 changelog，再把整份文档移入归档，不直接删除。
- 归档中的旧链接即使指向已删除文件也不修正——那是历史事实。

### 校验与例外

- 归档目录 `archive/` 不参与配对、领域地图、需求编号唯一性、changelog 存在性、引用与当日追加检查。
- 历史行校验采用双池：旧行在新活跃文档中找不到时，到活跃文档指针链接的归档文件中查找；两处都找不到即报错。
- 归档文件只允许追加：已有行被修改或删除即报错。
- 活跃 changelog 超过触发条件即报错；单节超限只告警。
- ADR 条目本身、需求正文与设计文档主体不归档，只归档各文档的 changelog。

## 需求编号与修改机制

### 编号规则

`R-<领域>-NNN`（如 `R-订单-001`、`R-财务-002`）：编号在领域内递增、永不复用；编号是身份不是版本——修改已有需求不换号、不加后缀，只有全新需求才取新号。领域更名时，历史需求编号保持不变；新需求按新领域名续号，从该领域现有最大号 +1 起。

### 修改流程

需求随时可以改：**正文直接改 + changelog 追记 + 编号不动**。

1. **改正文**：找到该需求所在小节（`product/<领域>.md`），直接改——正文只放当前真相，旧内容不留正文；
2. **记 changelog**：在该文档 changelog 当日小节末尾追加一行（类型「修改」，原本 / 现在 / 原因）；
3. **联动设计**：若改动影响实现，`design/<领域>.md` 同步改，并在其自身 changelog 记一行；
4. **改需求 vs 新需求**：业务上仍是同一件事 → 改原需求、编号不动；全新的一件事 → 新编号。拿不准用变更检验（该事项会随哪个领域的需求变化而改，即归哪）；
5. **撤销**：删除该需求小节 + changelog 记一行「删除」；编号随之作废、永不复用。

## 需求开发流程（SOP）

本节定义「一个需求从出现到完成」的标准流程。文档长什么样、怎么改，按本文档其余各节执行；本节只定义**顺序、卡点与完成定义**，不重复规则。

### 八步流程

| # | 步骤 | 产物 |
| --- | --- | --- |
| 0 | 调研原料 | 经营层调研文件（`.战略与经营/` 自由区，不进开发体系，只作输入） |
| 1 | 对齐 | 口径决策清单，**须用户拍板**（字段口径、计算规则、未建域处置、编号与精度） |
| 2 | 领域裁决 | 归属领域 + 需求编号；涉未建域只标【待补】+ 归属注记，不阻塞本轮 |
| 3 | product | `product/<领域>.md`：R-编号正文（What：字段口径、规则、页面设计、scope / feature 声明）+ changelog |
| 4 | design | `design/<领域>.md`：表归属、接口清单、算法、前端实现节 + changelog |
| 5 | ADR | 仅不可逆架构决策才落 `2-adr.md`；无则明确声明跳过 |
| 6 | 代码 | 契约先行：dto → `gen:openapi` → `gen:client` → 再写前端消费 |
| 7 | 验证 | 纯函数单测（最高优先级）→ 集成测试 → lint / typecheck / test / build / e2e；显示类改动加浏览器实拍；表单 / 详情页确认使用 PageFrame 并通过骨架 E2E |
| 8 | 收尾 | 核对文档与代码一致、changelog 齐全、引用无悬空；`pnpm docs:check` 通过 |

### 卡点（必须停下来等用户拍板）

- 第 1 步对齐结论；第 2 步归属有争议时；第 5 步涉及新依赖或不可逆决策。
- 其余步骤由 AI 按文档机制连续执行，不再逐个确认。

### 完成定义（DoD，全部满足才算完成）

1. product 与 design 成对存在，且正文与代码一致；
2. 每个动过的文档都有当日 changelog 行（历史行未动）；
3. 接口有变时契约已重建（openapi.json + 类型化 client）；
4. lint / typecheck / 测试 / build / e2e 全绿；
5. 无「只存在于对话里的约定」——所有决定都已落在文档或代码。

### 变更回路

需求随时可改：正文直接改 + changelog 追记 + 编号不动，代码同步——按本文档「需求编号与修改」节执行，不再另立规则。

## 新增功能的声明规则（scope / feature / 页面归属）

本节定义新增一个功能时必须声明什么。它与「需求开发流程（SOP）」配套：流程管顺序，本节管声明项。

### 三个正交维度

| 维度 | 回答的问题 | 归属 | 唯一维护位置 |
| --- | --- | --- | --- |
| scope | 这个租户里，谁能看 / 谁能操作 | 用户角色 | `product/账号与权限.md` R-账号与权限-003 权限矩阵 |
| feature | 这个租户有没有购买这个模块 | 租户套餐 | `product/租户.md` R-租户-003 功能清单 |
| 页面归属 | 这个页面由哪个领域定义 | 业务领域 | 本文档「前端与页面内容的归属」 |

### 四类开发情形

| 情形 | 典型例子 | 必须改的文档 | 动 feature | 动套餐 |
| --- | --- | --- | --- | --- |
| A 已有可售模块内加页面 / 字段 | 销售单加字段、客户列表加列 | `product/<领域>.md` ＋ `design/<领域>.md`，并声明 scope | 否，继承模块 feature | 否 |
| B 新增可售模块 | 工资、报价、对客端 | 新领域 product/design 配对 ＋ 总纲领域地图 ＋ 功能清单登记 | 是，登记一次 | 是；默认不进任何套餐，由运营决定 |
| C 运营后台功能 | 租户管理、套餐、平台账号 | tenant / auth / audit / platform 对应文档，并声明平台 scope | 否 | 否 |
| D 平台级跨租户能力 | 平台报表 | 先立 ADR ＋ 技术方案 | 否 | 否 |

一句话记忆（仅助记，冲突时以上表为准）：**加页面只声明 scope；开新模块才登记 feature；运营后台用平台 scope，与租户功能无关。**

### 校验顺序

登录 → 租户状态 → feature → scope。功能关闭不清数据，重新开启即恢复可见。

### 角色不变

租户内四角色固定不变（`ADMIN` / `SALES` / `FINANCE` / `WORKER`）；feature 是租户级开关，不改变角色与 scope 矩阵。租户自定义角色属独立需求，不在本条范围。

未声明 scope 的新页面视为未完成；未登记 feature 的新可售模块视为未完成。

## 文档定位

### 产品文档

- **回答**：What/Why——需求、约束、验收标准、**页面设计**。
- **位置与拆分**：`1-产品文档.md` 为全局总纲；各领域需求在 `product/<领域>.md`，与 `design/<领域>.md` 同名配对。
- **关键规则**：需求编号规则见本文档「需求编号与修改」；业务结构（领域地图 / 模块清单）与领域划分方法在总纲维护。

### ADR

- **回答**：为什么定死——不可逆的架构决策。
- **位置与拆分**：`2-adr.md` 单文件，按 `ADR-NNN` 分节。
- **关键规则**：只增不改——决策被取代时新增新条，不回头改旧条；优先级最高，冲突时以此裁决；每条自洽完整，不依赖外部讨论记录。

### 技术方案

- **回答**：全局怎么做——跨模块的约定、边界、规范。
- **位置与拆分**：`3-技术方案.md` 单文件。
- **关键规则**：全局约定的唯一出处，被所有模块设计文档引用。

### 模块设计文档

- **回答**：该领域具体怎么做——表结构、接口清单、状态机、算法与关键流程。
- **位置与拆分**：`design/<领域>.md`，**每领域一份**，与 `product/<领域>.md` 同名配对；主体为**后端**设计（数据模型细节、接口清单、状态机、算法与关键流程），另含**前端实现节**。
- **关键规则**：需求是改它的动作，不是它的单位——一个需求通常只更新一份（跨模块时更新多份），**不新增文件**。

## 前端与页面内容的归属

### 页面设计（属产品文档）

- 页面设计（这一页要有什么、怎么排、怎么交互）**归产品文档**（`product/<领域>.md`），作为对应需求的一部分——需求改则页面随之改，天然同步。
- 与前端实现的区别：页面设计=设计意图（人写，属 What）；前端实现=技术落地（AI 写，属 How）。

### 前端实现节（属模块设计文档）

本领域在**前端侧的技术落地设计**——回答前端代码怎么组织，而不是页面长什么样；它是页面设计（产品文档）与前端规范（技术方案 §7）之间的翻译层。**只在存在非平凡前端逻辑时写**（纯 CRUD 页面用现成组件拼即可，不为它单开一节）。

### 跨模块页面（归属与接口引用）

- **页面归属唯一**：一个页面必须且只能归属一个领域——判定看它**围绕哪个实体 / 业务动作**展开（如订单详情页虽展示报价与生产信息，主实体是订单，归 `order`）；拿不准时用**变更检验**（该页面会随哪个领域的需求变化而改）。**一个页面只能在一份文档里被描述**，禁止两份各写一半（否则即成两份真相）。
- **接口引用可跨模块**：数据来源项列出该页面调用的**所有**接口并标注归属领域，**只引用、不重述定义**（定义留在各领域的接口清单）。
- **数据聚合**：优先**客户端并发调用 + 客户端组合**；聚合逻辑复杂或需权限裁剪时，由**页面所属领域**提供**只读聚合接口**，内部只调其他领域的公开接口。
- **禁止**：新建聚合模块直接读他领域的表——属边界穿透，违反 ADR-001。

## 领域的特殊情况

本体系的「领域」默认指业务领域（清单见产品总纲领域地图）。平台自身机制——登录账号 `auth`、布局导航 `platform`——为特殊情况，作为平台领域，与业务领域同等遵守同名配对、需求编号、页面归属唯一等全部规则；无后端模块的平台领域（如 `platform`），其 design 文档仅含前端实现节，无后端主体。平台领域不是封闭清单：未来若出现其他类型的非业务领域，比照本条同等处理，不另立规则。
