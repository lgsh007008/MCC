# 需求开发流程

> 用途：把一个**具体需求**，在既定文档体系里走完——从需求定义、实现设计到测试验收与收尾。
> 形态：单文件，置于项目根目录，单独导入使用；**不含触发词、不自动启用**。

## 1. 定位与边界

- **做**：让一个具体需求在既定文档体系里走完。体系位于 `.AAAdocs/`：
  - `0-文档驱动开发机制.md`：文档机制、变更规则、changelog 纪律；
  - `1-产品文档.md`：产品总纲（What：全局）；
  - `2-adr.md`：架构决策记录（Why：只增不改）；
  - `3-技术方案.md`：技术方案（How：全局）；
  - `product/<领域>.md`：各领域需求；`design/<领域>.md`：各领域实现设计（同名配对）。
- **不做**：战略规划、商业分析、竞品分析；重新定义架构（架构已由 ADR 与技术方案锁死）。
- **例外出口**：一旦发现需要**不可逆的新决策**，立即停下，转 ADR 流程（新增一条 ADR），不自行拍板。

## 2. 停顿点协议（硬性 · 一律不许豁免）

本流程含五个停顿点 G0–G4。每个停顿点必须严格执行：

1. **只输出提案**（改哪个文件 / 哪一节 / 改成什么 / 配哪条 changelog），不落笔；
2. 输出后**立即结束本回合**，等待用户明确回复——对话式 AI 结束回合后无法自行继续，这就是硬挂起；
3. 未收到**明确确认**（如 确认 / 可以 / 继续）前，禁止修改任何文件、禁止进入下一个停顿点；
4. **含糊回复或沉默一律视为未确认**；
5. 禁止在同一回合内跨过停顿点，禁止一次改多份文档；
6. **不设豁免**：任何需求都必须逐点走完，不存在「全程授权一次走完」；
7. 可用时，借助提问 / 审批类工具把确认做成必须交互的一步（工具层加固）。

> 为什么：AI 天然倾向最短路径、一次改到底。停顿点把「提案 → 确认 → 落笔」的节奏强制成**一步一停**。

## 3. 流程

### 第 0 步 · 读体系（不改文件）

**必读（每次全读）**：

- `.AAAdocs/0-文档驱动开发机制.md`
- `.AAAdocs/1-产品文档.md`
- `.AAAdocs/2-adr.md`
- `.AAAdocs/3-技术方案.md`

**再读相关**：`.AAAdocs/product/<领域>.md`、`.AAAdocs/design/<领域>.md`（若已存在）。

**目的**：拿到**真实**的领域清单、全局口径、架构边界、已有需求编号。

> 领域清单**以产品总纲的领域地图与 `product/`、`design/` 目录的实际为准，不硬编码**——体系变了本流程不用改。
> 全读可避开章号 / 内容漂移，本流程**不写死任何章号**。

### 第 0.5 步 · 前置判定（不改文件）

| 判定 | 依据 | 结论影响 |
| --- | --- | --- |
| 属哪个领域 | 围绕哪个主实体 / 业务动作展开；拿不准用**变更检验**（会随哪个领域的需求变化而改） | 决定改哪份 `product/` 与 `design/` |
| 是否跨模块 | 会不会调用其他领域接口、改其他领域页面 | 决定要更新几份文档；接口只引用不重述 |
| 是否首个需求 | 该领域是否已有 `product/<领域>.md` 与 `design/<领域>.md` | 首个才创建两份文档（同名配对），否则只改 |
| 是否触及全局口径 | 是否改变全局规则 / 总纲 | 是 → 动 `1-产品文档.md`；否 → 只动分册 |
| 是否触及架构 | 是否需要不可逆的新决策 | 是 → 转 ADR 出口，不自行拍板 |

**停顿点 G0**：输出前置判定结论（领域 / 是否跨模块 / 是否新建文档对 / 是否触及全局 / 是否触及架构），等确认。

### 第 0.6 步 · 读现状代码（不改文件 · G0 确认后执行）

**领域确认后才读**，读的范围由 G0 结论限定，不多读。

- 该领域在 `apps/`、`packages/` 下的现有实现——按技术方案约定的目录定位，**不硬编码路径**；
- 数据模型现状：`packages/db` 的 schema；
- 已有的共享类型 / 令牌 / 组件；
- 该领域已有的测试代码所在位置。

**目的**：写下一条需求前先知道现状是什么。**没读过的代码不许写进设计与引用**。

### 第 1 步 · 需求定义（PM 视角）

- **改哪里**：`product/<领域>.md`；涉及全局口径才动 `1-产品文档.md`。
- **产出**：一个需求条目，字段见 §4 模板。
- **停顿点 G1**：输出条目草稿，等确认后才写入。

**PM 自检清单**

- [ ] 编号唯一、格式 `R-<领域>-NNN`（如 `R-订单-007`）
- [ ] 验收标准**逐条可判定**（非模糊描述）
- [ ] 不含战略 / 商业 / 竞品内容
- [ ] 页面设计只归属一个领域（一个页面只在一份文档里被描述）
- [ ] 未复制其他文档内容，一律引用

> 验收标准是否够格，由 PM 环节**自检**即可，不另设复核。

### 第 2 步 · 实现设计（Dev 视角）

- **改哪里**：`design/<领域>.md`。
- **产出**：
  1. 数据模型细节——**先读** `packages/db` 的 schema 核对现状，再写引用；引用须落到真实存在的表 / 字段，不复制表结构；
  2. 接口清单——**先读**本领域已有接口实现与代码生成的 OpenAPI，再列清单；跨模块接口只引用他领域、不重述定义；
  3. 状态机 / 关键流程；
  4. 算法（如报价、套裁）；
  5. 前端实现节——**仅存在非平凡前端逻辑时写**，含 6 项：页面 / 组件清单、数据来源、客户端状态、交互逻辑、组件复用、可见性与权限；
  6. 验收指针——测试代码路径 ＋ 验收结论位。
- **停顿点 G2**：输出设计草稿，等确认后才写入。

**Dev 自检清单**

- [ ] 未复制全局约定（全局约定回技术方案，只引用）
- [ ] 表结构只引用 schema；接口细节归 OpenAPI，不手写
- [ ] 未引入架构决策（有 → 转 ADR 出口）
- [ ] 前端实现节只写 6 项、不写 3 项（颜色 / 字号 / 间距、页面字段排布、接口定义）
- [ ] 只写本领域特有内容，全局约定一律不重复
- [ ] 跨模块接口只引用不重述
- [ ] 引用的 schema / 接口 / 已有类型，均已读过对应代码，且指向真实存在的对象

### 第 3 步 · 测试与验收（Test 视角）

- 逐条对照**验收标准**验收；先读（必要时运行）承载用例的**测试代码本体**，再下结论；用例不进文档。
- 验收指针里的测试代码路径必须是读到的**真实路径**；该领域无测试代码时，结论记**未覆盖**。
- 结论写入 `design/<领域>.md` 的**验收指针**：通过 / 例外 / 未覆盖。
- 回退：实现问题 → 回第 2 步；验收标准本身有误 → 回第 1 步并在 changelog 说明。
- **停顿点 G3**：输出逐条验收结论与例外 / 未覆盖项，等确认后才写入。

**Test 自检清单**

- [ ] 每条验收标准都有结论
- [ ] 记录了例外与未覆盖项
- [ ] 测试代码路径已写明，且为读到的真实路径

### 第 4 步 · 收尾

- 每份被改文档在 changelog **追加一行**（位置 / 类型 / 原本 / 现在 / 原因）；类型取 **新增 / 修改 / 删除**。
- 版本小节命名 `v<YYYYMMDD>`；**同一天只对应一个小节**（当天第二次变更就在该小节内追加新行），跨天才新增小节。
- 跑 §6 全局收尾检查清单。
- **停顿点 G4**：输出拟追加的 changelog 行 ＋ 检查清单结果，等确认后才写入。

## 4. 字段模板

### 需求条目模板（`product/<领域>.md`）

```
### R-<领域>-NNN <需求标题>

- 背景 / 目的：（为什么做）
- 功能描述：（做什么）
- 约束与边界：（不能做什么、限制条件）
- 验收标准：
  1. （逐条可判定）
- 页面设计：（这页要有什么字段、怎么排、怎么交互；不涉及页面则写 无）
- 跨模块引用：（要调的其他领域接口，只引用不重述）
```

### 模块设计条目模板（`design/<领域>.md`）

```
### R-<领域>-NNN <需求标题> · 实现设计

- 数据模型：（引用 packages/db 的 schema，不复制）
- 接口清单：（本领域接口；跨模块接口只引用他领域）
- 状态机 / 流程：
- 算法：
- 前端实现节：（仅非平凡前端逻辑时写，按 6 项）
- 验收指针：测试代码路径；结论（通过 / 例外 / 未覆盖）
```

## 5. 边界情形

1. **首个需求** → 先创建 `product/<领域>.md` 与 `design/<领域>.md`（同名配对），再按第 1 步起走。
2. **需求变更** → 改原需求条目，**不新增文件**；验收标准随之改、测试重跑。
3. **需求作废** → 从正文**移除**该条目（正文只放当前真相），changelog 记一行（类型：删除）。
4. **跨模块需求** → 更新多份 `design/`；接口只引用不重述；数据聚合优先客户端组合，复杂或需权限裁剪时由页面所属领域提供只读聚合接口，**禁止新建聚合模块直接读他领域的表**。
5. **需要不可逆决策** → 出本流程，新增一条 ADR（编号递增、作废号不复用）。

## 6. 生成纪律（写码时）

- **读码前置**：改任何文件前先读该文件本身与相邻调用方，禁止凭记忆或推测改码；
- **方案预审**：实现前先列方案与取舍，确认后再写码（即 §2 停顿点的「提案 → 确认 → 落笔」）；
- **重组件闸**：新增任何重组件（缓存 / 队列 / API 网关 / 搜索服务 / 独立 Worker 等）之前必须**单独提出确认**，不得随普通需求顺带引入；
- **diff review**：每次生成后，对照技术方案的边界纪律与各步自检清单逐条检查；
- **人工过目**：涉及 `.env`、API 契约、数据库迁移的改动，一律停下来交人工确认。

## 7. 全局收尾检查清单

- [ ] 单一事实源：无内容复制，只有引用
- [ ] 需求编号跨文档引用一致（`R-<领域>-NNN`）
- [ ] 只写本领域特有内容，全局约定不重复
- [ ] changelog 已按机制追加（位置 / 类型 / 原本 / 现在 / 原因）
- [ ] 版本小节 `v<YYYYMMDD>`，同日只对应一个小节
- [ ] 正文无英文双引号
- [ ] 文档文件名不带日期版本号
